## 1. 产品摘要

AI-APK-Tracer 面向 Android APK 漏洞挖掘场景，采用“基础包结构检查 → 可配置反编译 → 脚本规则预筛选 → 候选代码切片 → AI 深度语义分析 → 证据校验”的分层架构。系统先通过可测试、可版本化的执行脚本定位高价值候选，再由模型根据候选复杂度和证据需要自主扩展相关代码、调用链与配置上下文，最终输出按风险和置信度排序的发现。

> 术语说明：本文将配置项保留为 `source_analysis`，但产品展示统一称为“反编译代码级静态分析”。APK 反编译产物不是原始 Java/Kotlin 源码，通常是由 DEX 恢复的 Java 风格伪源码及 Smali，变量名、结构和行号可能失真。该能力不等同于运行时动态验证；动态沙箱验证仍保留在 P1。

产品不追求“告警越多越好”，而是追求：

1. **结论更准**：减少无效告警，优先暴露真实、高价值漏洞；
2. **证据更全**：结论可解释、可定位、可复核；
3. **复核更快**：降低安全研究员逐条排查和还原调用链的时间；
4. **持续变准**：把人工复核结果转化为可治理的评测与优化闭环。

## 2. 问题陈述

### 2.1 用户问题假设

> 以下问题来自对 APK 自动化检测场景的初步判断，尚未被历史数据验证。个人单机 MVP 不开展正式用户访谈；使用者可通过自己的扫描记录、误报样本和复核耗时持续修正这些问题假设。

移动安全研究员在使用自动化工具扫描 APK 时，可能面对以下问题：

- 告警缺少上下文，仅命中危险 API 或敏感关键词，无法证明漏洞真实可达；
- 同一根因产生大量重复告警，人工需要反复判断；
- 置信度与风险等级不可信，高危告警中混入大量误报；
- 结果缺少完整调用链、数据流、触发条件和修复建议，复核成本高；
- 人工判定结果没有形成结构化反馈，模型或规则迭代后无法证明效果变好。

### 2.2 不解决的代价

- 安全人员被低质量告警淹没，单位扫描任务的人工成本持续上升；
- 真正高风险漏洞被噪声掩盖，增加漏检和延迟修复风险；
- 用户对工具失去信任，最终退回纯人工分析。

### 2.3 已知事实、合理假设与待验证项

**已知事实**

- 项目目标是提高漏洞挖掘准确率并降低误报率；
- 项目场景与 APK 漏洞分析相关；
- 反编译代码级分析需通过配置文件显式开启，开启后先反编译 APK 再分析代码文件；
- 反编译代码默认先由执行脚本规则筛选候选，再由模型自主决定后续上下文扩展范围；MVP 暂不设置产品级上下文硬预算；
- MVP 漏洞覆盖优先聚焦 Android 四大组件；
- 项目必须按可维护、可测试、低耦合的工程规范建设；
- MVP 定位为本地单用户工具，不建设账号体系、多用户权限、项目隔离、审计后台、灰度发布或正式发布门禁。

**合理假设**

- 用户仅提交具有合法测试授权的 APK；
- MVP 以包结构/Manifest 检查、反编译代码级静态分析和多信号交叉验证为主，动态沙箱验证作为后续能力；
- 高风险结论需经人工复核，不由 AI 自动定责；
- 用户更重视可验证的少量高质量结论，而非大量低置信告警。

**待验证项**

- 当前工具或人工流程的 Precision、Recall、单任务复核时长基线；
- 首批支持的 APK 规模、加固类型、最低/目标 Android 版本；
- MVP 要覆盖的漏洞类型及其优先级；
- 单 APK 可接受的扫描耗时和资源成本；
- 本地运行所需的操作系统、硬件、模型接入方式及依赖环境；
- 样本、反编译代码和分析日志的留存与脱敏要求。

## 3. 目标与成功定义

### 3.1 用户目标

1. 安全研究员能优先处理最可能为真实漏洞的发现；
2. 每个漏洞结论均能看到来源、传播路径、关键代码和判定依据；
3. 研究员能快速完成“确认、误报、待定”复核并记录原因；
4. 扫描结果可直接形成结构化安全报告或后续工单输入。

### 3.2 业务与产品目标

1. 提高个人漏洞挖掘过程中的有效发现比例，减少明显误报；
2. 降低单条告警和单个 APK 的人工复核时长；
3. 记录模型、规则、提示词和分析引擎版本，使个人扫描结果可复现；
4. 将个人复核结果沉淀为规则测试样本和误报原因记录；
5. 通过脚本规则为 AI 提供高价值初始候选，再由模型自主扩展上下文；
6. 建立模块化、配置化、可测试的工程体系，使使用现有协议能力新增规则时不需要修改核心编排逻辑。

### 3.3 个人使用阶段观察项

> 个人单机 MVP 暂不建设固定盲测集、正式 Precision/Recall/F1 门禁或版本放行流程。以下数据仅用于个人判断工具是否变好，不阻塞运行和迭代。

- 每次扫描的候选数、人工确认数、误报数和待定数；
- 单条候选与单 APK 的人工复核时长；
- 重复告警数量及人工合并次数；
- APK 反编译成功/部分成功/失败状态；
- 各规则命中数、误报原因及个人确认结果；
- 扫描耗时、模型调用量和失败原因；
- 使用现有协议新增规则时的核心编排改动文件数，目标为 0。

## 4. 非目标（Non-goals）

MVP 明确不做以下事项：

1. **不承诺零误报或零漏报**：安全检测存在天然不确定性，产品以可量化改善为目标；
2. **不替代人工安全判断**：AI 输出候选结论和证据，最终漏洞确认、风险定级与责任判断由授权人员完成；
3. **不自动执行攻击或破坏性利用**：MVP 不生成或自动运行可直接用于未授权攻击的利用代码；
4. **不覆盖所有 Android 漏洞类型**：首版只支持经评审确认的高价值漏洞类型，其他类型进入后续路线图；
5. **不扫描未经授权的目标**：个人使用者只分析自己拥有或已获得测试授权的 APK；
6. **不建设多用户与企业管理能力**：账号体系、RBAC、项目隔离、组织审计、复杂工单、资产治理和 SLA 不纳入个人版 MVP；
7. **不建设正式发布治理体系**：固定盲测集、双人标注、专家仲裁、Precision/Recall/F1 发布门禁、灰度和自动回滚暂不实施；
8. **不让个人反馈自动训练或修改模型**：复核结果只作为个人记录和规则样本，是否用于后续优化由使用者主动决定。

## 6. 核心用户流程

1. **创建扫描任务**：上传 APK，确认合法授权，读取项目级扫描配置；
2. **基础检查**：解析 APK 元数据、Manifest、SDK 版本、权限和四大组件暴露面；
3. **按配置反编译**：当 `source_analysis.enabled=true` 时，在隔离环境中反编译 APK，产出 Java/Kotlin 可读代码、Smali 兜底文件、资源和代码索引；关闭时只执行基础检查，并明确降低覆盖范围；
4. **脚本规则预筛选**：执行独立规则脚本，扫描 Manifest 与反编译产物，定位四大组件入口、外部输入、权限缺口、敏感 Sink 和候选调用链；
5. **候选代码切片**：围绕规则命中的组件、方法和 Source/Sink 生成初始上下文，由模型根据调用关系和证据需要继续扩展相关代码；
6. **AI 深度语义分析**：仅分析规则输出及其代码切片，判断业务语义、校验逻辑、可达性、反向证据和潜在影响；
7. **确定性证据校验**：AI 引用的类、方法、行号和路径必须回查反编译产物，无法回查的内容不得进入事实证据；
8. **聚合与评分**：合并同根因告警，按风险、置信度、可利用性和证据完整度排序；
9. **人工复核与报告**：研究员确认、标记误报或待定，并输出结构化报告；
10. **个人反馈记录**：将复核结果保存为本地规则样本和误报记录；只有使用者主动操作时才用于调整规则、阈值或模型配置。

## 7. 用户故事

### P0 用户故事

1. **作为移动安全研究员，我希望按置信度和风险查看候选漏洞，以便优先复核最有价值的结果。**
2. **作为移动安全研究员，我希望查看漏洞从入口到危险点的完整证据链，以便判断漏洞是否真实可达。**
3. **作为移动安全研究员，我希望将结果标记为已确认、误报或待定并记录原因，以便沉淀可复用的质量反馈。**
4. **作为安全测试工程师，我希望看到扫描各阶段的状态和失败原因，以便及时恢复任务或定位问题。**
5. **作为安全测试工程师，我希望同根因的多个告警被合并，以便避免重复复核。**
6. **作为个人使用者，我希望记录不同引擎版本的扫描结果摘要，以便自行判断哪个版本更适合当前 APK。**
7. **作为规则维护者，我希望查看误报按漏洞类型和原因的分布，以便有针对性地调整规则。**
8. **作为安全研究员，我希望通过配置决定是否启用反编译代码分析，以便在扫描深度、耗时和数据处理范围之间做明确选择。**
9. **作为规则工程师，我希望把漏洞匹配逻辑实现为独立执行脚本并使用统一输入输出协议，以便测试、复用和版本管理，而不是依赖 Prompt 隐式约束。**
10. **作为安全研究员，我希望系统只把规则命中的相关代码切片交给 AI，以便在不占满上下文窗口的情况下获得深入分析。**
11. **作为维护者，我希望新增组件规则不需要修改核心扫描编排，以便降低回归风险和长期维护成本。**

### 边界与异常用户故事

1. **作为研究员，我希望证据不足的结论被明确标注为“待验证”，以便避免把推测当作事实。**
2. **作为研究员，我希望加固、反编译失败或分析不完整时看到覆盖缺口，以便正确理解扫描结论。**
3. **作为个人使用者，我希望扫描失败、文件损坏或本机资源不足时看到明确原因，以便自行恢复任务。**

## 8. 功能需求

### 8.1 P0：MVP 必须具备

**范围控制原则**

- MVP 主路径只包含“上传 → 基础检查 → 可配置反编译 → 脚本规则预筛选 → 候选代码切片 → AI 深度分析 → 人工复核 → 最小报告”；
- P0-1 至 P0-10 是个人单机版用户能力，P0-11 是工程可维护性要求；
- Activity、Service、ContentProvider、BroadcastReceiver 四个规则族均为 P0，不得在 MVP 中删除整个组件族；每个组件至少包含一条“外部暴露/权限”规则和一条“外部输入 → 敏感操作”规则；具体规则条目可在 Phase 0 冻结；
- 为每类规则建立 Android 版本语义矩阵、支持矩阵及阳性/阴性/边界夹具；夹具用于规则开发自测，不构成正式发布门禁；
- MVP 默认本地单用户运行，产品能力只包括任务配置、扫描、候选查看、个人三态复核和报告导出；
- 固定盲测集、双人标注、专家仲裁、账号/RBAC、项目隔离、组织审计、灰度发布和自动回滚均移至后续版本。

#### P0-1 扫描任务创建与授权确认

**需求**

- 支持上传 APK 并创建扫描任务；
- 校验文件类型、完整性、大小上限和重复文件；
- 用户创建任务前必须确认其拥有合法测试授权；
- 记录任务创建时间、APK 哈希、扫描配置及引擎版本。

**验收标准**

- Given 用户选择有效 APK，When 创建任务，Then 系统生成唯一任务并展示 APK 哈希与任务状态；
- Given 文件损坏、格式错误或超过上限，When 用户上传，Then 系统拒绝任务并给出明确原因；
- Given 用户未确认授权声明，When 提交任务，Then 系统不得启动扫描；
- 同一 APK 再次上传时，系统提示已有任务，但允许用户基于新版本引擎重新扫描。

#### P0-2 分阶段扫描与可观测状态

**需求**

- 至少展示：排队、基础检查、反编译、规则预筛选、代码切片、AI 深度分析、证据校验、结果聚合、已完成、失败；
- 若反编译代码分析关闭，则反编译、代码切片和 AI 深度分析阶段显示为“按配置跳过”，不得伪装成完整扫描；
- 每个阶段记录开始时间、结束时间、输入/输出摘要、版本和错误码；
- 对可恢复失败支持重试，重试不得产生重复结果。

**验收标准**

- 用户可查看当前阶段和历史阶段耗时；
- 任务失败时必须展示用户可理解的失败原因及建议操作；
- 分析不完整时，报告必须列出未完成模块及可能影响的漏洞覆盖范围。

#### P0-3 配置驱动的反编译代码分析

**需求**

- 扫描配置必须支持 `source_analysis.enabled` 开关，默认值、变更权限和环境差异由项目配置规范统一管理；
- 开启后先在隔离环境中反编译 APK，再对 Manifest、资源、DEX 反编译伪源码（通常为 Java 风格）和必要的 Smali 兜底文件建立索引；
- 反编译器必须可替换、可版本化，MVP 可选定一个默认实现，但核心流程不得与单一工具强耦合；
- 反编译适配器统一输出 artifact manifest，至少描述组件、DEX、Smali、伪源码、资源、符号映射、失败项、部分成功状态和内容哈希；下游不得直接依赖某个反编译器的私有目录结构；
- 记录反编译成功率、缺失类、失败文件、混淆/加固迹象、DEX/Smali/伪源码映射质量和工具环境指纹；
- 证据优先级为：原始 Manifest/资源/DEX 或 Smali 事实 > 反编译伪源码 > AI 推断；行号只能作为定位辅助，不能作为唯一证据；
- 产物哈希采用规范化文件路径、内容和排序计算，并同时记录反编译器、运行时和配置版本，避免环境差异导致“相同输入不同哈希”；
- 关闭反编译代码分析时，只输出基础组件暴露面和配置类发现，并在结果首页明确标注覆盖限制；
- 反编译产物按敏感代码处理，使用操作系统文件权限和个人本地存储/清理配置；不依赖 RBAC 或项目隔离能力。

**配置示例（字段名为产品约定，可在技术评审中调整）**

```yaml
source_analysis:
  enabled: true
  decompiler: jadx
  smali_fallback: true
  exclude_packages:
    - "androidx.*"
    - "kotlin.*"
  max_file_size_kb: 512
  decompile_timeout_seconds: 600
```

**验收标准**

- Given `source_analysis.enabled=true`，When 扫描有效 APK，Then 系统先完成反编译和索引，再进入代码规则扫描；
- Given `source_analysis.enabled=false`，When 扫描完成，Then 报告明确显示“未执行反编译代码级分析”及受影响的漏洞类型；
- Given APK 加固或部分反编译失败，When 输出结果，Then 系统列出失败范围，不得将未分析代码计为安全；
- 同一 APK、配置和反编译器版本重复运行，文件索引和哈希结果应保持一致。

#### P0-4 可执行脚本规则引擎与候选代码切片

**需求**

- 漏洞定位规则必须实现为独立可执行脚本或规则插件，不得只通过 Prompt 描述“应该检查什么”；
- Prompt 仅允许对规则命中的候选做语义判断、证据归纳和反向验证，不承担全仓代码搜索与基础模式匹配；
- 规则运行器使用版本化输入 Schema 读取 Manifest 索引、组件清单、代码符号、调用关系和配置；使用版本化输出 Schema 生成候选、证据位置、置信等级、待扩展调用节点和规则版本；
- 插件协议必须定义协议版本协商、能力声明、依赖、幂等要求、退出码、超时/部分成功语义、Schema 兼容策略和废弃周期；
- 每个规则包至少包含：规则元数据、执行入口、测试夹具、预期结果、适用 Android 版本、局限说明和内容哈希；
- 个人版只加载项目仓库内置规则，不支持运行时安装第三方规则；规则脚本在独立子进程中运行，并受 CPU、内存、输出大小和超时限制；
- 候选切片基于统一代码索引与调用/数据流中间表示，围绕命中组件、Entry Point、Taint Source、Sink 和鉴权/净化节点生成初始上下文；模型可根据分析需要继续扩展相关方法、类、组件和依赖；
- 切片器必须定义跨方法、继承/接口、回调、异步任务和跨组件跳转的扩展策略；反射、动态加载、Native 或无法解析的边必须标为覆盖缺口，而不是假定不存在；
- 第三方库、生成代码和重复片段默认排除；若其位于 Source → Sink 路径、承担鉴权/净化或被规则显式声明，则必须重新纳入切片；
- 规则结果必须可复现：记录 `rule_id`、规则版本、输入产物哈希、命中位置和执行日志；
- MVP 暂不设置单候选或单任务的文件数、Token、调用深度、扩片次数和候选数量硬上限；
- 模型根据候选复杂度、调用关系和证据完整性自主决定是否扩展上下文或继续多轮分析，系统不因预设预算主动截断有效分析；
- 规则预筛选仍是默认分析入口，用于定位高价值候选和提供初始证据，但不限制模型在确认漏洞所需范围内继续追踪相关代码。

**MVP 规则运行决策**

- 首选运行时固定为 Python 3.12.x，使用项目独立虚拟环境和锁定依赖；规则执行期间禁止在线安装依赖；
- 规则入口采用 `detect.py`，由运行器通过参数数组直接启动，不经过 Shell；输入为只读的版本化 JSON 文件，输出为标准输出中的单个 JSON 对象，诊断信息写标准错误；
- 规则默认按顺序执行，降低个人电脑资源争抢；后续可配置并发，但不得改变结果语义；
- 子进程工作目录固定为当前任务的 `rule-work/<rule_id>/`，环境变量采用白名单传递，不继承模型密钥、代理凭据和其他敏感变量；
- **运行器硬保证**：不经 Shell 启动、白名单环境变量、独立工作目录、stdout/stderr 上限、墙钟超时、进程组终止、退出码与 Schema 校验；
- **受信规则开发约束**：规则只读取运行器提供的 Manifest、索引和切片路径，只写自己的工作目录，不访问网络、不启动子进程、不执行 APK、不修改共享索引；普通 Python 子进程不能把这些约束变成强安全边界，因此由内置规则代码审查和契约测试保证；
- 内置规则属于受信代码，子进程隔离主要用于故障与资源控制，不声明为可抵御恶意第三方规则的强安全沙箱；未来若允许第三方规则，必须改用容器、受限系统用户或等效强隔离方案；
- MVP 首先支持 macOS；墙钟时间、stdout/stderr 和进程组终止由父进程硬执行，CPU/内存限制通过系统资源限制在可用时执行，临时目录配额通过运行器监测，后两者均标记为 best-effort 而非强隔离保证；
- 单规则初始默认值为：墙钟时间 120 秒、CPU 时间 60 秒、内存 1 GiB、stdout 10 MiB、stderr 10 MiB、工作目录 256 MiB；这些数值用于防止失控，不是分析完整性预算，可按规则夹具表现调整；
- 超时或超限时先终止整个规则进程组，短暂等待后强制结束；记录 `rule_failed`、已执行时间、资源原因和覆盖缺口，继续其他规则，失败规则不得产生半截候选；
- run manifest 记录 Python 实现、精确补丁版本、解释器路径、虚拟环境依赖哈希及各限制是否实际生效。

**验收标准**

- 新增一条使用现有协议能力的合规规则时，无需修改扫描编排核心代码即可被发现、执行和纳入报告；若需要新增索引或协议能力，必须通过 ADR、协议版本升级和兼容性测试，而不是在规则中绕过契约；
- 每条规则至少具备阳性、阴性、边界和异常输入测试，且可通过统一的本地校验命令独立运行；
- 深度分析的每个代码片段都能追溯到规则命中或显式调用链扩展请求；
- 超时、崩溃或输出不符合 Schema 的规则被隔离标记，不影响其他规则继续执行；
- 在个人维护的示例夹具中，预筛选规则不得漏掉已知阳性样本；MVP 不计算正式 Recall 或设置发布门禁；
- 扫描日志记录模型的上下文扩展路径、引用代码片段和扩展原因，保证分析过程可追溯；
- 当模型或服务自身达到能力边界、分析失败或返回不完整结果时，系统明确标记失败原因和覆盖缺口，并支持重试，不以产品预设上下文预算提前终止；
- 本地校验能够确认规则实际使用 Python 3.12.x 虚拟环境，运行期间未在线安装依赖；
- 规则进程只收到白名单环境变量，测试用模型密钥和代理凭据不得出现在规则进程环境或日志中；
- 超时、内存超限和超大输出均有异常夹具，触发后只终止当前规则并生成覆盖缺口；内置规则的代码审查和契约测试不得使用网络或子进程能力；
- 同一规则使用相同输入、版本和配置重复运行时，输出在规范化后保持一致；
- 规则脚本只能直接输出 L1 或 L2；AI 可以提出 L3 晋级建议，最终由确定性证据校验器检查 `blocking_gaps`、逐跳证据、Guard 状态和平台假设后确认；
- 反射、Native、动态加载、未解析调用边、分析阶段失败或依赖的服务端鉴权未知，且会影响漏洞成立时，必须写入 `blocking_gaps` 并阻止晋级 L3。

#### P0-5 多信号漏洞识别与四大组件优先覆盖

**需求**

- 采用统一的“外部可达性 × 保护强度 × 不可信输入 × 敏感操作”模型生成候选；
- MVP 优先覆盖 Activity、Service、ContentProvider、BroadcastReceiver 四大组件，先做组件有效导出状态、权限保护、调用者校验、外部输入和敏感 Sink 的组合判断；
- 扫描配置必须提供 `analysis_platform_api`，MVP 默认 API 36；所有有效导出、权限和动态 Receiver 结论都必须记录该平台假设；
- 有效导出状态必须结合组件类型、显式 `android:exported`、`intent-filter`、`targetSdkVersion` 和运行平台规则计算，输出 `true`、`false`、`conditional` 或 `unknown`，不得压缩为未经说明的布尔值；
- 建立版本化 Android 语义矩阵，至少覆盖 Activity/Service/Receiver/Provider 默认导出行为、`activity-alias`、application 与组件权限继承、自定义权限 `protectionLevel`、Provider read/write/path permission 与 URI grant、动态 Receiver 注册 API/flags/AndroidX 包装及受保护系统广播；
- 若结论随运行平台变化，结果必须列出适用 API 范围；自定义权限、系统广播或 URI grant 无法解析时标记 `unknown`，不得按“无保护”处理；
- 每项发现必须记录适用的 CWE、风险等级、置信度、规则 ID、命中证据和影响说明；
- 单一关键词、敏感类名、变量名、危险 API 或“未搜索到校验”只能用于候选排序，不得直接判定为高置信真实漏洞；
- 规则语义以 Android 官方文档和项目安全规范为准，参考文章只作为攻击面与候选规则输入，不作为唯一事实来源。

```yaml
android_semantics:
  analysis_platform_api: 36
  unresolved_permission: unknown
  platform_variant_result: conditional
```

**验收标准**

- 每类漏洞必须定义独立的证据充分性规则；两个高度相关的弱信号不能自动视为充分证据；
- 对每类漏洞至少通过一组阳性、阴性、边界和分析不完整测试样本；四大组件有效导出与权限判断必须覆盖 `activity-alias`、权限继承、自定义 protectionLevel、Provider path/URI grant、动态 Receiver flags 和平台版本边界；
- 同一 APK 在不同 `analysis_platform_api` 下语义发生变化时，结果必须显示不同平台假设或 `conditional`，不得生成无条件结论；
- 对不满足可达性或触发条件的结果，系统降低证据等级或标记为误报候选；
- 无法建立完整证据时，系统不得使用“已确认漏洞”措辞。

#### P0-6 证据链与可解释结果

**需求**

每项发现至少展示：

- 漏洞标题、类型、风险等级、置信度；
- 组件入口点（Entry Point，如生命周期回调）、不可信数据源（Taint Source）、危险点（Sink）、净化/鉴权节点及关键传播路径；
- 关键类、方法、文件、代码片段和行号（可获得时）；
- 组件暴露、权限、用户交互、系统版本等触发前提；
- AI 判定依据、支持证据与反向证据；
- 复核步骤、影响说明和修复建议；
- 模型、规则、提示词和分析引擎版本。

**验收标准**

- 研究员可从结果页跳转到对应代码位置；
- 证据链中任一环节缺失时，界面明确显示缺失项；
- 报告中的代码引用与当前扫描产物一致，不允许生成不存在的类、方法或行号；
- 系统必须将事实、推断和建议以不同标签展示。

#### P0-7 置信度、风险评分与排序

**需求**

- 风险等级与 AI 置信度分离：风险表示成功利用后的影响，置信度表示结论为真的可能性；
- 置信度由证据完整性、可达性、信号一致性、反向证据等共同决定；
- 支持按风险、置信度、漏洞类型、组件和复核状态筛选排序；
- 评分公式和阈值必须版本化，个人可切回历史配置。

**漏洞等级评判规则**

风险等级只表示“漏洞成立并被利用后的安全影响与利用门槛”，不得混入模型置信度。判级顺序固定为：确认安全影响 → 确认攻击者能力与前置条件 → 确认影响范围 → 得出等级；证据不足时标记“待定”，不能为了排序强行判级。

| 等级 | 必须满足的判定条件 | Android 四大组件典型场景 |
|---|---|---|
| **严重（Critical）** | 普通第三方应用或未认证攻击者可低交互、稳定实现任意代码执行、系统/高权限进程接管、跨应用大规模凭据窃取，或造成设备核心安全机制失陷；影响可跨用户、跨应用或长期持久化 | 导出组件直接形成 system/root 权限代码执行；可加载攻击者控制代码进入系统进程；可批量获取认证令牌并接管大量账号。单纯 `exported=true`、普通权限缺失或仅修改一项设置不得判严重 |
| **高危（High）** | 可绕过身份或签名权限边界执行高权限敏感操作，读取/修改大量高敏感数据，任意读写应用私有文件，接管账号/支付/管理能力，或对设备核心可用性造成显著影响；通常无需用户确认或仅需低交互 | 无权限 Activity 代理调用签名权限 Service 并修改系统设置；Binder/AIDL 未鉴权调用高权限能力；Provider 任意读取凭据/隐私数据库、任意写敏感数据或任意私有文件读写；广播触发支付、账户、权限或系统级状态修改 |
| **中危（Medium）** | 可确认的未授权读取、修改或操作具有实际安全/隐私影响，但影响范围有限、数据敏感度一般、需要特定前置条件，或不能直接接管高权限能力 | 导出组件触发有限业务操作；Provider 泄露单用户一般隐私或越权修改有限记录；URI 路径访问受限文件；隐式广播泄露一般敏感信息；Receiver/Service 可被外部触发并造成可恢复的明显状态改变 |
| **低危（Low）** | 影响有限且利用条件较高，仅造成少量非敏感信息泄露、局部可恢复异常、单应用短暂拒绝服务或安全加固缺失；不涉及有效权限绕过、高敏感数据或关键状态修改 | 可伪造广播只触发非敏感刷新/日志；导出组件导致应用局部崩溃；暴露版本、路径等有限信息；难以稳定触发且影响局限于目标应用 |
| **提示（Informational）** | 仅确认外部暴露、配置或启发式信号，尚无敏感 Source→Sink、权限绕过或实际影响证据 | L1 外部暴露事实、敏感类名命中、宽松 URI 匹配、未受限有序广播但没有敏感数据/安全结果。提示项不进入正式漏洞报告 |
| **待定（Pending）** | 影响、可达性、权限语义、Guard、服务端鉴权或平台假设存在关键缺口，当前无法可靠定级 | 导出状态为 `conditional/unknown`；依赖未解析反射/Native 路径；服务端是否二次鉴权未知且会决定漏洞是否成立 |

**判级修正规则**

1. **外部可达性**：普通第三方应用无需特殊权限即可触发，按表中等级判定；仅能通过 root、系统签名、已解锁调试设备或受保护系统身份触发时，通常降低一级或标记待定，除非这些能力正是漏洞绕过所得。
2. **用户交互**：无需交互不额外升级；必须经过清晰、不可欺骗的用户确认时通常降低一级。可被诱导、覆盖或绕过的确认不视为有效降级因素。
3. **权限与代理链**：攻击者无需持有目标签名权限，却可借助导出组件由目标应用自身调用受保护能力，视为真实权限边界绕过；按最终敏感操作的影响判级，而不是按入口组件类型判级。
4. **数据敏感度与规模**：认证令牌、支付数据、通信内容、精确位置、账号凭据、私有文件等按高敏感数据处理；批量、跨用户或可持续读取高于单条、单用户、一次性泄露。
5. **完整性与可用性**：修改账号、权限、支付、系统安全配置高于一般偏好设置；设备/系统服务持久不可用高于单应用可恢复崩溃。
6. **防护与前置条件**：有效签名权限、可靠调用者校验、严格参数白名单、不可绕过的二次鉴权会降低等级或使候选不成立；仅“未搜索到校验”不能作为升级依据。
7. **动态验证**：动态验证默认只改变置信度和验证状态，不自动改变风险等级；只有验证证明实际影响、攻击前提或影响范围与静态判断不同，才重新定级。
8. **最高影响约束**：同一根因存在多个可达 Sink 时，以证据充分的最高实际影响定级；不能用未证实的最坏情况抬高等级。

**规则输出与最终定级责任**

- L1 只能标记为提示；规则脚本的 `severity_hint` 只是建议，不是最终等级；
- L2 可给出“建议等级 + 判级依据 + 待确认条件”，关键影响未知时必须为待定；
- L3 经确定性证据校验器确认后可生成静态风险等级，但仍需个人复核才能写入“人工确认”报告；
- 最终结果必须保存 `severity`、`severity_reason`、`impact_scope`、`attacker_prerequisites`、`user_interaction` 和 `severity_version`；任何人工改级都要记录原等级与理由。

参考依据：[腾讯安全应急响应中心（TSRC）](https://security.tencent.com/)；[腾讯云 Android 组件安全测试参考](https://cloud.tencent.com/developer/article/1858083?policyId=1003)。当前会话无法访问已认证的腾讯内部知识库，以上规则结合公开腾讯资料与本项目 Android 静态分析边界制定。

**验收标准**

- 同一输入、同一版本和同一配置可重复运行并记录核心发现集合的 Jaccard 相似度，供个人观察模型波动；MVP 不设置硬阈值；
- 高风险低置信与低风险高置信结果不得混为单一排序维度；
- 结果页至少展示影响置信度的前三项因素及其方向（支持/反向），不得只展示黑盒分数；
- 仅命中导出/权限配置的 L1 结果必须为“提示”，不得判为严重、高危、中危或低危漏洞；
- 同一影响事实在 L2、L3 和动态验证成功阶段的风险等级原则上保持一致，只改变置信度/验证状态；若改级，必须能指出新确认的影响、前置条件或范围变化；
- “无权限 Activity 代理调用签名权限 Service 修改系统安全设置”在链路和影响证据完整时至少为高危；若只能证明页面可启动但敏感操作不可达，则降为提示或待定；
- 单纯导出组件、敏感命名或未搜索到 Guard 不得判严重；严重等级必须具有代码执行、系统接管、大规模账号/凭据影响等直接证据；
- 风险等级、置信度和证据等级分别存储并可独立筛选，任何字段不得互相覆盖。

#### P0-8 告警去重与根因聚合

**需求**

- 按根因、入口、危险点、传播路径和代码位置合并重复发现；
- 聚合后保留所有受影响位置和证据，不得因去重丢失影响范围；
- 支持展开查看子发现。

**验收标准**

- 个人可在同一示例 APK 上查看聚合前后告警数量，但 MVP 不设置下降比例门禁；
- 聚合后的主结论能追溯到全部原始发现；
- 研究员可手动拆分错误聚合并提交反馈。

#### P0-9 人工复核与结构化反馈

**需求**

- 支持“已确认、误报、待定”三态复核；
- 误报必须选择原因标签，可补充文本和证据；
- 建议原因标签：不可达、前置条件不成立、数据流错误、代码语义误判、重复告警、库代码/测试代码、模型幻觉、风险等级不当、其他；
- 所有状态变更保留时间和前后值，个人可查看和撤销；
- 复核结果仅保存在本地任务数据中，不自动训练或修改模型。

**验收标准**

- 用户不能在没有原因的情况下提交“误报”；
- 用户可撤销或修改自己的复核结论，并查看本地修改历史；
- 不建设专家审核、多人冲突仲裁、签名或组织审计流程；
- 个人可按漏洞类型、模型版本和误报原因查看自己的复核记录。

#### P0-10 结构化报告与强制模板

**需求**

- 支持查看和导出 Markdown 格式漏洞报告；后续新增 HTML、PDF 等格式时，其章节顺序和内容语义必须与 Markdown 主模板一致；
- 单漏洞报告必须严格遵守来源样例 `/Users/perrinlei/a.md` 的章节结构、顺序和内容逻辑，不允许模型自由增删、合并或调整一级章节；开发时须将其脱敏后纳入项目内版本化 fixture，运行时和本地校验不得依赖项目外个人目录；
- 报告模板作为版本化资产管理；模板变更由个人使用者确认，并运行固定样例快照测试；
- 报告叙事必须遵循“应用版本与环境 → 漏洞入口与前置条件 → 完整利用链路 → 权限/信任边界绕过 → 实际危害与等级 → POC 与验证结果 → 修复方案”的逻辑；
- 报告必须正交记录“发现状态”和“动态验证状态”：人工复核只能确认静态证据与漏洞判断，设备状态变化、界面现象、利用成功/失败等运行时事实只能来自关联的动态执行记录；
- AI 候选可以输出报告草稿，但不得虚构测试环境、截图、POC 执行结果或运行时影响；即使已人工确认，只要未执行动态验证，相关运行时字段仍必须保持“未执行/待验证”；
- 批量任务先输出任务级摘要和覆盖/限制说明，再为每个漏洞按同一单漏洞模板生成独立章节或独立文件；单漏洞模板内部结构不得改变；
- 所有类名、组件名、权限、方法、属性、Action、命令和版本号必须回查扫描产物或人工输入；不能回查的内容不得作为事实写入报告。

**单漏洞报告强制结构**

```markdown
## 版本
android:versionCode="<值或未获取>"
android:versionName="<值或未获取>"
android:compileSdkVersion="<值或未获取>"
android:compileSdkVersionCodename="<值或未获取>"
package="<包名>"
发现状态：<AI候选/待定/人工确认/误报>
动态验证状态：<未执行/成功/失败/结果不确定>

## 测试环境：
<设备型号、系统/ROM 版本；未执行动态验证时固定填写“未执行动态验证，仅完成反编译代码级静态分析”>

## 漏洞描述
<组件/入口 + 暴露或权限缺陷 + 外部可控输入 + 关键分支/方法 + 高权限敏感操作 + 成立条件>

<证据图片或证据引用；无图片时固定填写“证据引用：<artifact/slice/finding ID 与代码位置>”>

## 漏洞链路：
<攻击者入口>
→ <外部触发方式及可控参数>
→ <组件入口/生命周期方法>
→ <关键校验或分发逻辑>
→ <跨方法/跨组件代理调用>
→ <受保护能力或敏感 Sink>
→ <最终状态变化或安全影响>

<单独说明原有权限/信任边界，以及攻击者如何借助导出组件或代理链路绕过；未证实时标记“待验证”>

漏洞危害：<严重/高危/中危/低危/待定>
攻击者可利用此漏洞：<具体影响、必要前提、影响对象和边界；不得写脱离证据的夸张场景>

## POC
<AI候选/待定：固定填写“待人工确认，不输出未经复核的可执行 POC”；人工确认但未执行：填写“未执行 POC；建议复核步骤：<步骤>”；已执行：填写实际最小复现命令/步骤>

POC结果：<未执行时固定填写“未执行动态验证，结果待确认”；已执行时填写成功/失败/结果不确定及可观察现象>

## 修复方案
<首选根因修复，例如取消不必要导出、增加签名级权限、调用者身份校验、参数白名单或服务端二次鉴权>

<补充纵深防御措施>
```

**字段与内容逻辑**

| 章节 | 必填内容 | 事实来源与约束 |
|---|---|---|
| 版本 | versionCode、versionName、compileSdkVersion、Codename、package | 仅来自 APK/Manifest 解析；缺失写“未获取” |
| 状态 | 发现状态、动态验证状态 | 两个字段正交记录；人工确认不得自动改变动态验证状态 |
| 测试环境 | 设备、系统/ROM 版本 | 仅来自动态执行记录；未执行时使用固定文案，人工静态复核不得补写 |
| 漏洞描述 | 入口、外部可控条件、关键调用、敏感操作、成立前提 | 必须与后续链路一致，不先下超出证据的结论 |
| 证据引用 | 截图或 artifact/slice/finding ID、文件/类/方法位置 | 图片缺失不保留虚假图片名；所有引用必须可打开或可追溯 |
| 漏洞链路 | 从攻击者入口到最终 Sink 的逐跳路径 | 每一跳必须存在代码、Manifest 或人工验证证据；推断跳转需显式标记 |
| 权限绕过说明 | 原保护权限/信任边界、代理组件、攻击者所需权限、绕过原因 | 四项均必填；无权限边界时写“不适用”并说明原因 |
| 漏洞危害 | 等级、已证实影响、潜在影响、前置条件、影响对象与边界 | 动态影响未验证时必须区分“静态推断”，不得写成已发生事实 |
| POC | 未复核占位、未执行复核步骤或实际执行步骤 | 只有人工确认且获得授权后才可展示可执行步骤；系统不得自动执行 |
| POC结果 | 未执行、成功、失败或结果不确定及可观察现象 | 只有关联动态执行记录才能写成功/失败/不确定；人工静态复核不能解锁运行时结论 |
| 修复方案 | 根因修复 + 纵深防御 | 必须对应漏洞链路中的暴露点、校验缺口和敏感操作 |

**状态与输出矩阵**

| 发现状态 | 动态验证状态 | 测试环境 | POC | POC结果 | 运行时影响措辞 |
|---|---|---|---|---|---|
| AI候选/待定 | 未执行 | 固定未验证文案 | 固定不输出文案 | 固定未验证文案 | 只能写“可能/静态推断/待验证” |
| 人工确认 | 未执行 | 固定未验证文案 | 可写“未执行 POC；建议复核步骤” | 固定未验证文案 | 不得写成已发生事实 |
| 人工确认 | 成功 | 实际设备与系统 | 实际执行步骤 | 成功现象与证据 ID | 可写已观察到的事实 |
| 人工确认 | 失败 | 实际设备与系统 | 实际执行步骤 | 失败现象、错误与证据 ID | 不得宣称成功利用，需说明静态判断与动态结果差异 |
| 人工确认 | 结果不确定 | 实际设备与系统 | 实际执行步骤 | 不确定原因与证据 ID | 保留“待进一步验证” |
| 误报 | 任意 | 按实际情况 | 不输出利用 POC | 记录误报原因 | 不输出漏洞成立或危害结论 |

**可执行报告数据契约**

- 报告生成前必须先形成结构化 `report_payload`，至少包含 `app_version`、`finding_status`、`dynamic_validation_status`、`environment`、`description`、`evidence_refs`、`chain_steps`、`trust_boundary`、`impact`、`poc`、`poc_result` 和 `remediation`；模型不得直接绕过该数据契约自由生成最终报告；
- `chain_steps` 每一步必须包含节点类型、显示文本、证据 ID 和证据状态（事实/推断/缺失）；
- `trust_boundary` 必须包含原保护权限或信任边界、代理组件、攻击者所需权限和绕过原因；不适用字段需显式填写原因；
- `impact` 必须区分已证实影响与潜在影响，并关联前置条件、影响对象和边界；
- `remediation` 必须至少映射一个链路缺陷：暴露面、权限、调用者校验、参数校验、敏感操作或服务端鉴权；
- 报告渲染器只负责按固定模板映射字段；章节结构由代码模板控制，不由模型自由决定。

**验收标准**

- 给定同一结构化 finding 输入，生成报告的一级章节名称和顺序与强制模板 100% 一致；
- 版本字段必须全部出现，缺失值使用“未获取”，不得删除字段或猜测；
- “发现状态”和“动态验证状态”必须同时出现并符合状态矩阵；人工确认但未动态执行时，测试环境和 POC 结果仍使用固定未验证文案；
- 未执行动态验证时，不得生成设备型号、ROM 版本、截图名称、成功/失败现象或已发生的运行时影响；
- “漏洞描述”“漏洞链路”“权限绕过说明”“漏洞危害”“POC”“修复方案”中的组件、权限、方法、参数和 Sink 必须引用同一组结构化实体并通过一致性校验；
- 漏洞链路至少覆盖攻击者入口、外部可控参数、组件入口、关键分支/校验、敏感 Sink 和最终影响；每一步均须带证据状态，缺失环节标记“证据不足”，不能用流畅文字掩盖；
- AI候选/待定状态不得输出可执行 POC，不得使用“已成功利用”“用户无需确认”等确定性结果措辞；
- 人工确认但未执行动态验证时，可以输出明确标记为“未执行”的建议复核步骤，但不得填写成功/失败结果；
- 动态验证状态为成功、失败或结果不确定时，必须关联验证时间、环境和原始验证证据；个人使用者自行确保验证对象与设备已获授权；
- 报告中每条事实证据都能追溯到 Manifest、反编译产物、规则命中、代码切片、人工输入或动态验证记录；
- 导出结果与页面当前筛选范围一致，并在任务级摘要明确筛选条件；
- 扫描不完整时，任务级报告首页必须显示醒目限制说明，各漏洞报告同步标注受影响的链路环节；
- 使用样例报告对应的固定 fixture 执行本地模板快照测试：解析 Markdown AST，严格比较一级章节名称与顺序，再校验必填字段和状态文案；仅允许对 fixture 声明的版本号、包名、设备、时间、证据 ID 等动态字段做归一化；
- 模板快照测试同时校验跨字段关系：描述、链路、权限绕过、危害、POC 和修复方案引用的组件、权限、参数与 Sink 一致；链路每一步具备证据 ID/状态；修复项能够映射到至少一个已识别缺陷。

#### P0-11 工程规范化与低维护成本

**需求**

- 按职责拆分反编译适配器、产物索引、规则运行器、上下文切片、AI 分析、证据校验、结果聚合和报告模块，模块间只通过版本化数据契约通信；
- 配置采用 Schema 校验和分层覆盖，优先级统一为“内置默认值 < 项目配置 < 单次任务配置”；密钥不得写入配置仓库；
- 规则、模型、Prompt、Source/Sink 字典、反编译器和报告模板分别版本化，并由每次扫描的 run manifest 固化实际版本组合，避免结果不可追溯；
- 统一错误码、结构化日志、任务 `trace_id`、指标命名和产物目录；为 artifact、slice、candidate、finding 分配不可变 ID、父子关系和内容哈希，禁止模块自行发明互不兼容的格式；
- 建立单元测试、规则夹具测试、Schema 契约测试和少量端到端样本测试，供个人开发时按需运行；不建设正式盲测和发布门禁；
- 提供一个本地校验入口，统一执行格式检查、静态检查、单元测试、规则契约校验和示例扫描；校验失败时明确输出原因，但不设计多人合并审批流程；
- 依赖版本必须锁定；升级反编译器、模型 SDK 或规则运行时后至少运行相关模块测试和示例扫描；
- APK、反编译器和规则脚本均按不可信输入处理：只在项目工作目录或隔离临时目录内读写，拒绝路径穿越和恶意压缩条目，默认不执行 APK 内代码，规则进程默认无非必要网络访问并设置超时/资源限制；
- 本地服务如需启动 Web 界面，默认只监听回环地址，不提供远程访问和账号体系；
- 采用语义化版本和变更记录；破坏性配置或数据契约变更必须提供迁移说明；
- 关键架构决策使用 ADR 记录，模块必须提供最小使用说明、输入输出和故障排查信息；
- 默认提供标准规则模板和脚手架，降低新增规则时的目录、Schema、测试和文档重复劳动。

**建议模块边界**

```text
config -> apk_ingest -> decompiler -> artifact_index
                                  -> rule_runner -> context_builder
                                  -> ai_analyzer -> evidence_verifier
                                  -> finding_aggregator -> report
```

**建议仓库结构**

```text
src/                  # 核心编排与领域模块
rules/                # 按组件和 rule_id 管理的独立规则包
schemas/              # 配置、索引、候选、发现等数据契约
tests/unit/            # 核心模块单元测试
tests/contract/        # 模块与规则 Schema 契约测试
tests/integration/     # 端到端扫描测试
tests/fixtures/        # 已授权、脱敏的 APK/代码夹具
config/                # 可提交的默认配置和环境示例
docs/adr/              # 关键架构决策记录
scripts/               # 开发、校验、回归等统一入口
```

**验收标准**

- 在干净环境中可按项目说明完成依赖安装、配置校验、测试和示例 APK 扫描；
- 无效配置在任务启动前失败，并返回具体字段和错误原因；
- 使用现有协议能力的新规则只增加规则包和测试，不修改核心编排模块；新增平台能力必须通过 ADR 和协议升级流程；
- 每条规则必须通过其声明的阳性、阴性、边界和异常夹具；核心模块测试覆盖率作为观察项，不设 MVP 硬阈值；
- 本地校验命令可独立运行并返回明确成功/失败状态，个人开发者自行决定是否继续使用当前版本；
- 固定输入、配置和版本生成的候选 JSON 字段稳定、顺序可规范化、结果可复现；
- 恶意压缩路径、超大文件、规则超时和工作目录越界均有最小自动化测试；
- 任一发现可以通过 `trace_id` 追溯到配置、反编译器、规则、代码切片、模型和证据校验版本。

### 8.2 四大组件首批规则与证据充分性

> 本节参考 [《Android 漏洞挖掘-四大组件漏洞》](http://kvancy.top/2025/07/02/Android漏洞挖掘-四大组件漏洞/) 提炼攻击面。规则语义以 Android 官方文档、版本语义矩阵和个人证据复核为准。

**统一证据等级**

- **L1 外部暴露事实**：脚本能够从 Manifest、SDK 版本或注册 API 确定组件外部可达且未发现强权限保护；只进入“外部暴露面清单”，不默认命名为风险或漏洞，避免把 Launcher、公开 Deep Link 和公共 Provider 误报为问题；
- **L2 静态漏洞候选**：L1 成立，并存在外部输入或外部调用到敏感操作的可追溯链路；鉴权、参数校验或净化状态仍需 AI 深入判断；
- **L3 高置信静态候选**：入口、Source、传播路径、客户端保护缺口、关键 Guard、Sink 和触发前提均有证据；必须区分“Guard 确认缺失”和“Guard 存在但可绕过”，并给出对应证据。服务端鉴权默认标记为 `unknown`；若漏洞成立依赖服务端行为且无独立证据，则阻止晋级 L3；仍不得描述动态执行结果；
- **人工确认**：个人复核 L3 证据后才能将发现状态改为“人工确认”；动态验证状态仍独立记录。

**MVP 冻结规则**

| 组件 | 规则 ID | 规则输出边界 | 达到 L2/L3 所需证据 | 必须降级的情况 |
|---|---|---|---|---|
| Activity | `ACTIVITY_EXPORTED_NO_PERMISSION` | L1 外部暴露事实 | 有效导出状态、组件权限及 protectionLevel 均可确定；若要达到 L2，需与该 Activity 内敏感页面/操作或下一条 Source→Sink 规则关联 | 仅凭类名敏感、导出状态受版本影响但无法确定、存在有效签名权限 |
| Activity | `ACTIVITY_INTENT_TO_SENSITIVE_SINK` | L2/L3 候选 | 导出 Activity；`Intent` Action/Extras/Data URI 可控；存在到文件、WebView、组件跳转、账户/配置修改等 Sink 的逐跳路径；L3 还需证明 Guard 缺失或可绕过 | Source 与 Sink 不连通、参数已做严格白名单/路径规范化、敏感操作需不可绕过的二次鉴权 |
| Service | `SERVICE_EXPORTED_NO_PERMISSION` | L1 外部暴露事实 | 有效导出状态、Started/Bound 类型和保护权限可确定；若要达到 L2，需关联敏感服务操作或可调用 IPC 接口 | Service 仅执行无害操作、存在有效签名权限、仅系统可达 |
| Service | `SERVICE_BINDER_CALLER_CHECK_MISSING` | L2/L3 候选 | 导出 Bound Service 返回 Binder/AIDL；至少一个外部方法可达敏感操作；L3 需检查入口、基类、代理层和公共函数，均不存在有效 UID/签名/权限校验 | 只因当前方法未搜索到校验；接口仅做无害计算；校验位于共享入口或代理层 |
| Service | `SERVICE_IPC_INPUT_TO_SINK` | L2/L3 候选 | `onStartCommand` Intent、AIDL 参数或 `Parcel.read*` 为 Source，并到达文件、数据库、受保护组件或高权限能力；L3 需证明调用者和参数校验不足 | 参数不可控、路径不可达、Sink 前存在有效调用者校验或业务二次鉴权 |
| ContentProvider | `PROVIDER_READ_WRITE_PERMISSION_MISSING` | L1 外部暴露事实 | 有效导出状态；分别解析通用、读、写、path permission 和 URI grant；若要达到 L2，需证明 CRUD/openFile 暴露敏感数据或可修改受保护状态 | Provider 明确设计为公共数据源、权限保护充分、相关接口未实现或拒绝访问 |
| ContentProvider | `PROVIDER_CALLER_CHECK_MISSING` | L2/L3 候选 | 外部可达 CRUD/openFile/applyBatch；操作涉及敏感数据或状态；L3 需覆盖入口、基类和 DAO 调用链，确认无 UID、包名、签名或权限校验 | 仅做负向关键词搜索、校验位于公共层、数据本身公开 |
| ContentProvider | `PROVIDER_URI_TO_FILE` | L2/L3 候选 | URI path/segment 到 `File`、`FileInputStream` 或 `ParcelFileDescriptor` 的数据流；L3 需证明 canonical path/固定映射/基目录约束缺失或可绕过，目标范围包含非公开文件 | 使用安全 FileProvider 映射、canonical path 与基目录校验完整、路径不可控 |
| ContentProvider | `PROVIDER_SQL_STRUCTURE_INJECTION` | L2/L3 候选 | 可控 selection、projection、sortOrder 或 URI 片段进入 SQL 结构或字符串拼接；L3 需证明攻击者可改变查询结构；`selectionArgs` 仅作为值绑定证据，不自动视为安全或危险 | 所有结构均为固定模板，只有值通过占位符绑定，且不存在可控列名/排序/表名拼接 |
| ContentProvider | `PROVIDER_UNAUTHORIZED_QUERY` | L2/L3 候选 | 外部调用可控制查询范围并读取敏感列/行；L3 需证明缺少调用者、字段或行级授权，且返回结果对外可见 | 数据公开、列和行范围受固定白名单约束、调用者身份与数据归属校验完整 |
| ContentProvider | `PROVIDER_UNAUTHORIZED_MUTATION` | L2/L3 候选 | insert/update/delete/applyBatch 接收外部 ContentValues 或条件并修改敏感字段/他人数据；L3 需证明字段/行级授权缺失 | 敏感字段被剔除、对象归属校验完整、操作仅影响调用者自己的数据 |
| BroadcastReceiver | `RECEIVER_EXPORTED_NO_PERMISSION` | L1 外部暴露事实 | 静态 Receiver 有效导出且无有效接收权限；若要达到 L2，需关联 `onReceive` 中的敏感操作 | 仅接收受保护系统广播、逻辑无害或存在有效签名权限 |
| BroadcastReceiver | `DYNAMIC_RECEIVER_EXPORTED_NO_PERMISSION` | L1/L2 候选 | 解析注册 API、`RECEIVER_EXPORTED/NOT_EXPORTED` flags、sender permission 和 Action；自定义外部 Action 可触发业务逻辑时达到 L2 | Receiver 实际为 NOT_EXPORTED、仅受保护系统广播可触发、注册时指定有效 sender permission |
| BroadcastReceiver | `RECEIVER_INPUT_TO_SINK` | L2/L3 候选 | `onReceive` 的 Action/Extras/Data 为 Source，并到达组件启动、文件、数据库、网络或状态修改；L3 需证明来源、签名、token 或业务状态校验不足 | 外部输入未参与敏感操作、存在不可绕过校验、Sink 不可达 |
| BroadcastReceiver | `IMPLICIT_BROADCAST_SENSITIVE_DATA` | L2/L3 候选 | 敏感数据进入广播 Extras；Intent 未指定 component/package，发送时无接收权限；L3 需证明普通第三方应用可注册接收且数据确属敏感 | 显式广播、限定包名、签名权限保护、数据为公开或不可由第三方接收 |

**仅作辅助信号，不单独出报告**

- `ACTIVITY_SENSITIVE_NAME_HINT`：Reset、Password、Admin、Payment、Debug 等命名只用于排序；
- `PROVIDER_LOOSE_URI_MATCH`：宽松 URI 匹配只作为 Provider 路径和授权规则的加权证据；
- `ORDERED_BROADCAST_UNRESTRICTED`：未限制有序广播只作为辅助候选，必须关联敏感数据或可被篡改的安全结果后才能升级。

**统一判定原则**

- “未搜索到校验”属于负向证据，不能单独达到 L3；必须检查父类、代理层和公共 Guard。服务端鉴权无法从 APK 证明时记录为 `unknown`，不得写成“缺失”；
- 同一根因被多条规则命中时合并为一个候选，并保留全部规则 ID 与证据；
- L1 只进入外部暴露面清单，L2/L3 才进入 AI 深度分析和漏洞报告草稿；
- 任一链路环节为推断或缺失时必须在报告中明确标记，不能用高置信措辞掩盖。

### 8.3 P1：显著改善体验

## 10. 本地数据与运行安全底线

个人版不建设身份认证、RBAC、项目隔离、组织审计和安全运营流程，但仍保留以下本机运行底线：

1. **合法授权**：使用者只分析自己拥有或已获得测试授权的 APK；
2. **本地目录约束**：APK、反编译产物、日志和报告只能写入配置的项目目录或隔离临时目录，禁止路径穿越和任意覆盖其他文件；
3. **不执行目标代码**：静态分析阶段不得安装、启动或执行 APK 内代码；动态执行属于 P1；
4. **规则进程隔离**：规则脚本默认无非必要网络访问，并设置超时、CPU、内存和输出大小限制；
5. **外部模型提示**：调用外部模型前明确提示代码将离开本机；是否允许发送由使用者在配置中决定；
6. **本地密钥处理**：模型密钥通过环境变量或本机密钥存储读取，不写入项目配置、日志和报告；
7. **个人清理能力**：使用者可手动删除单个任务的 APK、反编译产物、模型输入缓存和报告；
8. **远程访问关闭**：如提供本地 Web 界面，默认仅监听回环地址，不开放远程访问。

### 10.1 默认数据根目录

- 默认数据根目录为 `<workspace>/.ai-apk-tracer/`，必须加入 `.gitignore`；允许通过配置改到其他本地目录；
- 每次扫描创建独立 `run_id`，格式为 `<UTC时间>_<APK-SHA256前12位>_<随机后缀>`；不同任务不得共享可变文件；
- 输入 APK 复制到任务目录，禁止使用可跳出数据根目录的软链接；原始 APK 永不修改、移动或删除；
- 目录默认仅当前操作系统用户可读写；日志默认不记录密钥、完整模型请求或大段代码内容。

```text
<workspace>/.ai-apk-tracer/
├── runs/
│   └── <run_id>/
│       ├── manifest.json       # APK 哈希、配置、组件版本、阶段状态
│       ├── input/app.apk       # 输入 APK 的任务副本
│       ├── decompile/          # DEX 伪源码、Smali 与资源
│       ├── index/              # Manifest、符号、调用/数据流索引
│       ├── rule-work/          # 每条规则的隔离工作目录
│       ├── rule-results/       # 原始候选 JSON
│       ├── slices/             # 提供给模型的代码切片
│       ├── ai-cache/           # 当前任务模型请求缓存
│       ├── findings/           # 聚合后的结构化 finding/report_payload
│       ├── reports/            # Markdown 报告及引用证据包
│       ├── logs/               # 结构化阶段与错误日志
│       └── tmp/                # 可随时删除的临时文件
```

MVP 不引入 `trash/` 回收区，避免“已删除但仍占空间/仍可访问”的语义歧义。完全删除经确认后直接执行文件系统删除；不承诺 SSD 或文件系统层面的物理安全擦除。

### 10.2 默认保留与按任务清理

- 默认保留策略为 `manual`：任务完成后自动删除 `tmp/` 和已退出进程残留，其他产物保留，避免个人复核期间证据丢失；
- 报告生成或更新 finding 时，将所有保留 finding 的事实引用复制为只读、自包含的 `reports/evidence/` 证据闭包，不只复制当前报告可见引用；清理前必须验证保留对象不再依赖待删除的 index/slices/decompile 文件；
- **精简中间产物**：删除 `input/`、`decompile/`、`index/`、`rule-work/`、`rule-results/`、`slices/`、`ai-cache/`、`logs/` 和 `tmp/`，保留 `manifest.json`、`findings/`、`reports/` 与 `reports/evidence/`；该模式仍保留敏感代码证据，不得称为隐私清除；
- **清除敏感内容**：删除 APK 副本、全部代码/索引/切片/模型缓存、findings、reports、evidence 和日志，只保留经过字段白名单脱敏的 manifest 摘要与清理历史；
- **完全删除任务**：删除整个 `<run_id>` 目录，必须明确二次确认；个人版不得批量删除多个任务；
- 清理前展示将删除和保留的分类、敏感内容提示、绝对路径与预计大小；
- 清理器使用不跟随软链接的目录遍历和相对目录句柄执行删除，不仅依赖预先 `realpath` 检查；拒绝软链接、`..`、空 `run_id`、数据根目录本身及任何跨任务路径；
- 清理开始前在 manifest 写入 `cleanup_in_progress`、模式和计划；每类产物删除后记录结果，结束状态为 `completed`、`partial` 或 `failed`，支持幂等重试；错误记录写入保留的 manifest 清理历史，而不是即将删除的 logs；
- 清理操作永不触碰用户提供的原始 APK 路径；启动时可清理超过 24 小时的孤立 `tmp/`；任务缓存默认仅属于当前任务，不建设跨任务共享缓存。

**存储配置示例**

```yaml
storage:
  data_root: ".ai-apk-tracer"
  retention: manual
  stale_tmp_hours: 24
  copy_input_apk: true
  shared_cache_enabled: false
cleanup:
  default_mode: prune_intermediates
  available_modes:
    - prune_intermediates
    - clear_sensitive_content
    - delete_run
  keep_manifest: true
  keep_findings: true
  keep_reports: true
  keep_report_evidence: true
  no_follow_symlinks: true
  require_confirmation_for_full_delete: true
```

**验收标准**

- 任一任务的所有生成文件都位于自己的 `<run_id>` 目录，manifest 可列出各类产物路径和大小；
- 精简中间产物后，APK 副本、反编译文件、切片、任务缓存和日志已删除，保留 finding 与报告的全部事实引用仍可通过自包含证据包打开；
- 清除敏感内容后，不再保留 APK、代码片段、模型输入输出、finding 或报告正文，仅保留脱敏 manifest 摘要和清理历史；
- 完全删除单个任务不会影响其他任务、项目源码或用户原始 APK；
- 使用软链接、路径穿越、伪造 `run_id` 或清理期间替换目录项的请求会被拒绝或安全中止；
- 模拟中途失败后，manifest 状态为 `partial` 或 `failed`，再次执行同一清理可幂等完成；
- 任务异常退出后重新启动，系统可识别未完成状态并清理其孤立临时目录。

## 11. 关键风险与缓解措施

| 风险                   | 影响               | 缓解措施                              |
| -------------------- | ---------------- | --------------------------------- |
| 为减少误报过度收紧候选规则 | 漏掉真实漏洞 | 保留宽松候选层，定期人工抽查未深入分析的规则命中 |
| AI 生成虚假代码路径或证据 | 严重损害结果可信度 | 证据只能引用分析引擎实际产物；不存在的实体禁止输出 |
| 加固、混淆导致分析不完整 | 结论覆盖不足 | 显示能力边界和覆盖缺口，不做过度承诺 |
| 个人复核判断不稳定 | 误报记录和规则调整出现偏差 | 保留证据、复核备注和状态修改历史，允许后续重新判断 |
| 用户样本或代码发送到外部模型 | 敏感代码泄露 | 默认由配置显式决定是否调用外部模型，并提示数据边界 |
| 单 APK 推理成本过高 | 个人使用成本增加 | 先记录实际消耗，不以固定上下文预算限制分析；需要时由使用者切换模型 |
| 代码切片丢失关键上下文 | AI 误判可达性或鉴权 | 支持调用链扩展请求、父类/跨方法补片和上下文不足标记 |
| 反编译失真或加固失败 | 错误代码证据与覆盖盲区 | 产物哈希、Smali 兜底、覆盖缺口报告和失败样本标记 |
| 规则脚本数量增长失控 | 维护成本和回归风险上升 | 插件契约、模板、语义化版本、废弃标记和规则夹具 |
| 本地处理恶意 APK/压缩条目 | 覆盖项目外文件或耗尽资源 | 隔离目录、不跟随软链接的删除/遍历、路径校验、超时和资源限制 |
| 精简后仍保留敏感证据 | 用户误以为代码已被清除 | 明确区分精简中间产物、清除敏感内容和完全删除三种模式，并展示保留内容 |
| 自动生成复现步骤被滥用 | 安全风险 | MVP 不自动执行；使用者只在授权设备和环境中手工验证 |

## 16. 产品决策原则

1. **高质量证据优先于更多告警**；
2. **个人版通过实际扫描和人工复核观察效果，不建设正式 Precision/Recall/F1 发布门禁**；
3. **事实必须来自可追溯分析产物，AI 不得补造证据**；
4. **高风险结论必须支持个人复核，动态事实必须来自真实执行记录**；
5. **每次范围新增都要考虑个人维护成本，避免为未来团队场景提前建设**；
6. **模型和规则版本由使用者基于实际结果自行切换，不建设灰度与自动回滚系统**；
7. **确定性匹配必须落为可执行、可测试、可版本化的规则脚本，不把工程逻辑藏在 Prompt 中**；
8. **深度分析以规则命中和代码切片为初始入口，模型可根据候选复杂度和证据需要自主扩展相关上下文，MVP 暂不设置产品级上下文硬预算**；
9. **使用现有协议能力新增规则时不修改核心编排；新增平台能力必须走 ADR 与协议升级，配置、接口、错误码、日志和测试遵循统一规范**。
