# 04 - 规则体系

## 规则总览

## 规则协议

### rule.yaml 格式

每条规则目录下必须包含 `rule.yaml`：

```yaml
id: SERVICE_BINDER_CALLER_CHECK_MISSING    # 规则唯一标识
severity: high                             # 建议等级（P6 单源化：必须与 RULE_META 一致）
version: 1.0.0                              # 规则语义版本
protocol_version: 1.0.0                     # 规则协议版本
component: service                          # 组件类型
evidence_output: L2                         # 输出证据等级
builtin: true                               # 内置规则标记
entrypoint: detect.py                       # 规则入口文件
android_api: "1-36"                         # 适用 API 范围
limitations: "检测 Binder Stub 的调用者校验缺失，不覆盖运行时动态注册的 AIDL 接口。"
```

P6（severity 单源化）：全部 `rule.yaml` 必须携带 `severity` 字段，且取值必须与 `rules/shared/detector.py` 的 `RULE_META` 建议等级一致，规则侧不能另设等级。该约束由 `backend/tests/test_webview_crypto_rules.py` 的 `TestSeveritySingleSource` 强制校验。

### 规则输入

规则通过 `input.json` 接收输入，包含：

```json
{
  "protocol_version": "1.0.0",
  "manifest": {"...": "AndroidManifest 解析结果"},
  "config": {"...": "分析配置"},
  "index": {
    "schema_version": "当前索引版本",
    "type": "sqlite",
    "root": "/absolute/decompile/sources",
    "database_path": "/absolute/run/index/analysis.sqlite3",
    "database_relative_path": "index/analysis.sqlite3",
    "allowed_index_root": "/absolute/run/index",
    "stats": {},
    "skipped_files": [],
    "content_sha256": "..."
  }
}
```

`protocol_version` 由 runner 注入；当前输入没有 `rule_id`/`run_id` 字段，也不是单独的 `index_path`。规则**不接收完整 `code_index`**，只通过 `RuleIndexReader` 在 `allowed_index_root` 内以 SQLite `mode=ro&immutable=1` 查询版本匹配的共享索引。关闭源码分析时 `index` 可为 `null`，Manifest-only 规则仍可运行。

### 规则输出

规则通过 stdout 输出 JSON：

```json
{
  "protocol_version": "1.0.0",
  "rule_id": "SERVICE_BINDER_CALLER_CHECK_MISSING",
  "status": "completed",
  "candidates": [
    {
      "rule_id": "SERVICE_BINDER_CALLER_CHECK_MISSING",
      "rule_version": "1.0.0",
      "component": "service",
      "component_name": "com.example.MyService",
      "evidence_level": "L2",
      "locations": [{"artifact": "code", "path": "...", "line": 42}],
      "sources": [{"kind": "binder_transaction", "path": "...", "line": 42}],
      "sinks": [{"kind": "binder_reply_disclosure", "path": "...", "line": 100}],
      "propagation_paths": [{"text": "transaction 1 → getToken → reply.writeString", "status": "fact"}],
      "guard_status": "absent",
      "authorization_status": "unprotected",
      "deterministic_chain_verified": true,
      "blocking_gaps": []
    }
  ],
  "component_diagnostics": [
    {
      "component_name": "com.example.MyService",
      "status": "completed",
      "duration_ms": 12.3,
      "gaps": []
    }

}
```

Runner 当前强制每个 candidate 至少包含 `rule_id`、`rule_version`、`component`、`evidence_level`、`locations`，且规则只能直接输出 L1/L2。`component_diagnostics` 是可选对象数组；当前主要由 Binder 规则逐组件输出。Runner 会为 diagnostics/gap 补充 fail-closed `coverage_domain`，未完成或含 critical gap 的组件进入 run 级 `component_coverage_gaps`。不要把示例中的可选 Source/Sink 字段误当成所有规则统一必填字段。

## 共享库

### rules/shared/detector.py

统一检测引擎，处理所有 34 条规则的 `execute(rule_id, payload)` 入口，包含：

- L1（清单级）与 L2（源码级）分层判定
- Source/Sink 模式匹配
- Guard 检测（checkCallingPermission, enforceCallingPermission 等）
- Binder/AIDL transaction 解析
- Provider 操作模式、SQL 注入、URI 边界分析
- 授权矩阵评估与覆盖缺口标记

### rules/shared/index_reader.py

共享只读索引读取器，提供：

- `component_flow_scope(component_fqcn, entry_names)` — 获取组件闭包
- Binder 批量 JOIN 查询
- FTS 全文检索
- 禁止前导 `% LIKE` 和 N+1 查询

### rules/shared/dataflow.py

方法级数据流分析引擎：

- `ValueFact` — 值版本化与 strong update/kill
- `FlowState` — Intent/Bundle key-slot 覆盖
- `VALIDATED_SLOT_OVERWRITTEN` — 校验后覆盖检测
- `ROUTER_VALIDATION_BYPASS` — Router 校验绕过
- 跨方法返回值与对象 mutation 摘要
- Fragment 反射、started Service 状态机、dynamic Receiver 绑定

### rules/shared/authorization.py

Effective Authorization Matrix 评估：

- application/component/alias/provider/path permission
- URI grant
- protectionLevel 矩阵
- Sink 级 GuardCoverage

### rules/sink_taxonomy/versions.yaml（sink taxonomy 单一事实源）

sink taxonomy 的单一事实源（single source of truth），`rules/sink_taxonomy/` 目录下仅此一个文件；backend 侧零依赖红线（backend 不 import rules 模块），该文件是两侧唯一的共享数据层。当前 `taxonomy_version: 1.0.6`，共 82 条 = `source: base` 73 条（自 `dataflow.py` 内置 family 提炼的种子）+ `source: manual` 9 条（人工追加）。

- **双源结构**：每个条目声明 `source: base` 或 `source: manual`；`method` × receiver（`receiver_leaves`/`receiver_prefixes`/`receiver_exact`）定位调用形态。
- **verified_arity 三态语义**：条目可选 `verified_arity` 字段。带 `verified_arity` 的条目在 dataflow 回退路径做与内置 family 等价的 arity 三态校验（verified / OPERATION_SIGNATURE_GAP / not_sensitive），保持确定性闭链能力；不带 `verified_arity` 的条目产出 custom_sink 提案形态（`verified=False` + 非 critical gap，供下游知悉非确定性分类）。
- **dataflow manual 回退消费**：`rules/shared/dataflow.py` 的 `_manual_sink_table()`（约 L2750-2797）加载 manual 条目（进程级缓存；yaml 缺失/解析失败时优雅降级为空表）。内置平台 family 不命中时回退查 manual 条目（`method` × receiver 匹配，见 classify_operation_taxonomy 尾部回退分支，约 L3214-3219）。
- **人工追加闭环**：`scripts/promote_custom_sink.py`——从 run 探索候选确认（用法 A）或直接确认方法名（用法 B），执行 promote（taxonomy 版本化追加）→ revalidate（升档对比报告）→ 可选 golden 用例生成；`backend/app/analysis/sink_taxonomy.py` 据此做 `custom_sink_proposal` 判定。单人操作约定，版本冲突在 git 层解决。

## 第一批规则不变量

这些不变量是当前确定性规则的 fail-closed 边界；无法证明时应产生 gap、L1 或不报告，不能交给 AI 猜测：

| 不变量 | 当前约束 |
|---|---|
| 生命周期签名 | 组件入口必须匹配 Android 生命周期的名称和参数签名；例如动态 Receiver 只接受精确 `onReceive(Context, Intent)`，同名 overload 不作为入口 |
| receiver-aware taxonomy | Sink/API 分类同时验证 method descriptor 与可信 framework receiver type；应用类即使叶子名为 `WebView`、`Service` 等也不能当作 Android 敏感 API |
| Receiver flags/permission/action | 解析 platform `Context`、`ContextCompat` 与 legacy overload，联合 `RECEIVER_EXPORTED`/`NOT_EXPORTED`、注册 permission、IntentFilter action、protected-broadcast catalog 和 API 分支；overload/表达式不明时保留 critical gap |
| Binder transaction/reply | 候选绑定到 concrete `onTransact` case、transaction code/descriptor 和实现方法；返回泄露只有 `reply.write*` 的实参确实来自该 transaction 的 dispatch 结果时成立，不能借用其他 case |
| Provider overload/query sensitivity | 只接受有效 ContentProvider 生命周期 overload；query 敏感性绑定实际投影/SQL 选择列或返回证据，方法文本中出现 `token` 等词不能充当证明 |
| Guard dominance | Guard 必须在同一候选、同一 transaction/路径上确定性支配 Sink；条件结构或控制流无法证明时为 `present_partial`/`GUARD_DOMINANCE_UNKNOWN`，不能判有效 |
| canonical boundary | 文件/URI 边界使用 canonical 路径及目录分隔符边界、paths XML、authority/URI grant/permission 联合判断；仅字符串前缀或“配置看起来安全”都不能替代边界证明 |
| chain identity | 语义集合字段规范排序，但传播路径保持顺序；`scope_key`、有序 `chain_key`、`deterministic_fact_hash` 全相同才可去重或传播代表项 AI observation，聚合不得跨候选拼链 |

动态 Receiver 的分层遵守上述约束：只证明注册暴露时为 L1；注册点、Receiver 类型、精确生命周期入口、外部输入到已验证副作用均闭合且无 critical gap 时才为 L2。

## 规则扩展开发

### 新增规则步骤

1. 在 `rules/<component>/` 下创建规则目录
2. 编写 `rule.yaml`（参考现有规则格式）
3. 编写 `detect.py`，实现 `execute(rule_id, payload)` 函数
4. 使用 `rules/shared/detector.py` 的统一检测引擎
5. 使用 `rules/shared/index_reader.py` 查询索引
6. 在 `backend/tests/` 添加测试
7. 运行 `scripts/check-backend.sh` 验证

### 规则开发注意事项

- 规则只直接输出 L1/L2；L3 只能由 evidence validator 基于候选自身的确定性证据晋级，AI observation 不能单独晋级
- 规则不能把完整 code_index/content 复制到工作目录
- 规则不能执行 APK 代码
- 规则失败和组件 gap 按覆盖域传播
- 证据校验只称 `evidence_integrity_validation`
- Binder 必须确认 AIDL/onTransact transaction
- FileProvider 必须联合 paths XML、模式、URI grant、权限、canonical 边界和 authority 冲突判断

### sink taxonomy 同步校验（CI 强制）

修改 `rules/shared/dataflow.py` 或 `rules/sink_taxonomy/versions.yaml` 后必须运行 `scripts/check_sink_taxonomy_sync.py` 校验双源一致性。脚本做四态判定：CONFLICT（error，退出码 1——base 条目的 receiver 证据探针与 dataflow 冲突）、ORPHAN（warning——条目全部 receiver 证据在 dataflow 均不命中）、PASS_WITH_INFO（仅部分证据命中）、COVERAGE（info——dataflow 签名分支中的 method 名不在 versions.yaml base 中）。该校验已接入 pytest CI：`backend/tests/test_sink_taxonomy.py` 的 `test_versions_yaml_synced_with_dataflow`（:493，subprocess 断言在约 L505）以子进程方式运行脚本并断言退出码为 0，CONFLICT 即构建失败。
