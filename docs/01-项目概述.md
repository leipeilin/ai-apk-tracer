# 01 - 项目概述

## 产品定位

AI-APK-Tracer 是一个**本地单用户**的 Android APK 安全自动化分析工具。它采用分层分析：确定性规则与索引发现攻击面和静态链，candidate funnel 做路由与精确去重，方法级切片向 AI 提供受控上下文；AI 在 L1 triage、L2 review、探索轨、核验与报告草稿等受控阶段只返回 strict observation，证据回查、dataflow、Guard、授权与最终 decision 仍由确定性代码和人工复核负责。

核心目标：**提高真实漏洞检出准确率，降低误报率与人工复核成本。**

## 解决什么问题

传统 APK 安全工具有两个极端：

| 方式 | 优点 | 缺点 |
|---|---|---|
| 纯规则扫描 | 快、确定性强 | 误报高、无法理解语义 |
| 纯 AI 分析 | 语义理解强 | 慢、成本高、不可重复 |

AI-APK-Tracer 的方案是**分层协作**：

1. **规则/索引层**做确定性攻击面、Source/Sink、dataflow、Guard 与授权分析
2. **Funnel 层**按 chain identity 做确定性路由、精确去重和 AI 预算选择
3. **切片层**提供受预算约束的方法级上下文，而非整文件投喂
4. **AI 层**做 L1 triage、L2 review、必要的 finalization observation 和格式 repair，以及可选的探索轨（explorer/deep-dive，默认关闭）、多轮核验（verify，默认关闭）与报告草稿（report，经 API 按需触发）；可以解释、提议和请求扩片，不能写确定性事实或最终 decision。探索轨以规则预扫产物为引导主动检索代码，其 validated 探索候选与规则候选同走 funnel 路由与复核，partial/unverified 不进入正式 finding
5. **Evidence/decision 层**回查引用并独立裁决事实完整性、语义链、可利用性与 review 状态

## 核心能力

### 1. 规则覆盖四大组件与全局代码模式（34 条）

| 类别 | 规则数 | 典型漏洞 |
|---|---|---|
| Activity | 3 | 无权限导出、Intent 注入敏感 Sink、外部路由注入（外部输入决定启动目标/被全量透传） |
| Service | 3 | 无权限导出、Binder 无调用者校验、IPC 输入到 Sink |
| ContentProvider | 6 | 读写权限缺失、URI 到文件、SQL 注入、未授权查询/修改 |
| BroadcastReceiver | 4 | 无权限导出、动态 Receiver 暴露/闭链、输入到 Sink、隐式广播敏感数据 |
| 辅助信号 | 3 | 敏感 Activity 名称提示、松散 URI 匹配、有序广播无限制 |
| Manifest 配置 | 3 | debuggable 调试、allowBackup、明文流量 |
| WebView | 5 | JS Bridge 暴露、FileAccess/UniversalAccessFromFileURLs 开启、SSL 错误忽略、加载外部内容 |
| 密码学/证书校验 | 5 | TrustManager 全接受、HostnameVerifier 恒真、ECB 弱模式、弱算法/弱哈希、硬编码密钥 |
| Intent | 1 | PendingIntent 可变 |
| 日志 | 1 | 敏感数据写日志 |

### 2. 方法级上下文切片

不是把整个 Java 文件丢给 AI，而是：

- 从代码索引中提取类、方法、行范围、继承关系、调用关系
- 围绕候选 Source/Sink/入口点生成精确切片
- AI 只能通过结构化请求（method/class/component/callers/callees/file_symbols）扩片
- 扩片以完成、无新上下文或重复请求自然终止

### 3. 三级证据模型

| 级别 | 含义 | 典型来源 |
|---|---|---|
| L1 | 攻击面候选 | 规则匹配 Manifest/代码模式 |
| L2 | 静态候选 | 规则完成 Source/Sink/位置回查 |
| L3 | 高置信静态候选 | 候选自身的确定性证据通过 evidence validator 晋级；AI observation 不能单独晋级 |

L1 不进入正式漏洞报告；L2/L3 可生成 Markdown 报告。证据等级不替代最终 evidence decision 或人工 review。动态 Receiver 在只确认注册暴露时输出 L1；仅当注册→精确 `onReceive(Context, Intent)`→已验证副作用链闭合且无关键 gap 时输出 L2。

规则候选之外，探索轨（可选，默认关闭）会产出独立的**探索候选**（explorer candidates，产物类 schema 见 `schemas/explorer_candidate.schema.json`）。探索候选经三档校验（validated/partial/unverified），仅 validated 候选归一化并入候选池、与规则候选同走 funnel；未通过校验的探索候选 0 条进入正式 finding，留在 `explorer/candidates.json`，人工可通过 `GET /api/runs/{run_id}/explorer/candidates` 查看。

### 4. 确定性 Guard 校验

不依赖 AI 判断 Guard 是否有效，而是用确定性逻辑评估：

- `checkCallingPermission` / `enforceCallingPermission` 等 Guard 调用
- Manifest 权限的 protectionLevel 矩阵
- FileProvider canonical 路径边界
- Binder transaction 级别的调用者校验

### 5. AI 任务级熔断

- 无代码 preflight：先测试 AI 连通性、鉴权和 strict JSON 能力
- 全局不可恢复错误可触发任务级断路；单候选格式、上下文或预算问题局部隔离
- L1/L2/finalization 的 AI 输出均为 observation；AI 失败或建议不覆盖确定性 Guard/dataflow/authorization/decision 结论
- 默认 `ai.enabled=true`、`ai.allow_external_code=true`，选中候选的方法级代码切片可能发送到外部 OpenAI-compatible 服务；探索轨（`explorer.enabled`）、核验轨（`verify.enabled`）、API 入口表（`api_surface.enabled`）与资产/批量扫描（`assets.enabled`）为可选能力，默认关闭

## 适用场景

- 安全研究员对 Android 应用做自动化初步扫描
- 企业安全团队对内部应用做批量安全检查
- 漏洞赏金猎人快速定位高价值攻击面
- 安全教学/培训中演示 Android 组件漏洞

## 不适用场景

- 动态分析/运行时监控（本工具是纯静态分析）
- 大规模云端 SaaS 部署（设计为本地单用户）
- 需要多用户/RBAC/审计的团队协作场景（未来团队版规划）
- 非 Android APK 分析（不支持 iOS/其他平台）

## 安全底线

即使个人使用，系统也保留本机安全底线：

- 隔离目录：任务专属产物在 `.ai-apk-tracer/runs/<run_id>/` 下；内容寻址共享 AI cache 位于 data root 的独立 `ai-cache/`
- 路径穿越/恶意压缩防护
- 不执行 APK 代码
- 规则进程网络/超时/资源限制（墙钟 120s、CPU 60s、内存 1GiB）
- 外部模型显式配置，密钥不落日志
- 本地 Web 仅监听 127.0.0.1 回环地址
- 按任务清理产物；单 run cleanup 不删除 run 外共享 AI cache，外部 provider 数据也不受本地清理控制

## 验证口径

真实性能、候选数和 Finding 数依赖 APK、JADX、规则/索引版本及预算配置，不在文档中固定历史样本数字。验证当前实现时应记录本次 run 的：

- APK/hash、JADX 与 pipeline/schema/index 版本；
- rule failure、component diagnostics 与 coverage gap；
- funnel candidate/identity/selected/deferred 汇总；
- AI preflight、完成/失败/未完成及 peak concurrency；
- evidence integrity、decision、聚合与人工 review 状态。

run 安全配置快照会记录协议级 `provider_kind` 与 model；finding 未记录的 provider/model，以及 AI stage 未汇总的 cache、stop reason、L1/L2 分轨统计，应显示为“未记录/未汇总”，不得用默认值猜测。

## 离线评估与回归门槛

仓库顶层 `evaluation/` 维护离线评估体系：`golden/v1` golden 数据集（dataset v3，29 个用例，含探索轨命中标注 `explorer_expected`）与 `baselines/` 基线（m4-health、m4-shop）。`backend/app/evaluation/` 的 gate 将当前评估指标与基线对比（缺指标或低于基线减容差即 BLOCK），CLI 退出码 0=ALLOW / 1=BLOCK。该体系定位为开发侧质量门槛，不参与单次 run 的线上裁决；流程见 `docs/evaluation-workflow.md`。
