# 06 - 使用指南

## 1. 环境与启动

需要 Python 3.12、Node.js 20+ 和 JADX。

```bash
# 后端
scripts/dev-backend.sh

# 前端
scripts/dev-frontend.sh
```

生产构建：

```bash
cd frontend
npm install
npm run build
```

后端默认仅监听 `127.0.0.1`。

## 2. AI 默认值与隐私提醒

默认配置保持：

```yaml
ai:
  enabled: true
  allow_external_code: true
```

这意味着选中的候选可将**方法级代码切片**发送给配置的外部 OpenAI-compatible 模型服务。上传前应确认：

1. 你拥有 APK 分析授权；
2. 代码外发符合组织、客户和数据驻留要求；
3. provider/model 适合处理该代码；
4. 不允许外发时，应在启动前将 `AI_APK_TRACER_AI__ALLOW_EXTERNAL_CODE=false`；
5. 如需完全禁用 AI，将 `AI_APK_TRACER_AI__ENABLED=false`。

配置示例：

```bash
export AI_APK_TRACER_AI__ENABLED=true
export AI_APK_TRACER_AI__ALLOW_EXTERNAL_CODE=true
export AI_APK_TRACER_AI__BASE_URL="<OpenAI-compatible endpoint>"
export AI_APK_TRACER_AI__MODEL="<model-id>"
export AI_APK_TRACER_OPENAI_API_KEY="<secret>"
```

前端显示 enabled、外发许可、协议级 `provider_kind`、model 和 AI 阶段状态，不显示 `base_url` 原文、API key 或密钥环境变量名。当前 run API 返回的 `provider_kind=openai-compatible` 只表示协议族，不是具体供应商身份；历史 run 或 finding 缺失 provider/model 时界面明确显示“未记录”。

## 3. 创建扫描

1. 上传 APK；
2. 勾选合法授权确认；
3. 选择是否执行源码分析；
4. 创建 run；
5. 在 run 详情确认 AI 外发与隐私提示是否符合预期。

## 4. 阅读阶段时间线

### `candidate_funnel`

重点指标：

- candidate：规则候选数；
- exact dedupe：完全相同 identity 的重复数；
- AI representative：实际代表项；
- L1 selected：本次进入 AI triage；
- deferred：因任务预算延后。

`deferred` 不是误报，也不表示安全。

### `ai_analysis`

重点指标：

- completed/failed/incomplete；
- peak concurrency；
- cache hit（当前 stage summary 未汇总时显示“未汇总”，单 finding 仍可能有记录）；
- stop reason（当前 stage summary 通常未统一汇总，应查看单 finding/trace）；
- L1 selected/deferred 应查看 `candidate_funnel`；当前 AI stage 尚未汇总 L1/L2 分轨摘要。

AI 请求成功只表示服务/协议成功，不表示证据闭环或漏洞成立；finalization 生成的 verdict/review recommendation 也只是 observation。

## 5. 阅读 Finding

### 对象类型

| 显示 | 含义 |
|---|---|
| L1 exposure | 外部暴露或攻击面事实；动态 Receiver 只闭合到注册暴露时属于此层 |
| L2 静态链 | 已有确定性 Source/Sink/传播候选链；动态 Receiver 需闭合注册→精确 onReceive→已验证副作用 |
| L3 高置信链 | 通过更多确定性门禁；仍需区分静态与动态结论 |

### 四层状态

- Funnel：候选如何被路由；
- Analysis：AI 是否完成；
- Evidence：证据支持、未解决、仅暴露或反驳；
- Review：待 AI、待人工、AI 反驳、人工误报、人工确认。

### 三个可信度状态

- `fact_integrity_status`：事实引用是否有效；
- `semantic_status`：静态链是否闭合；
- `exploitability_status`：是否达到定级条件。

即使 UI 显示“语义链已闭合”，也不要直接写成“漏洞成立”。还要检查授权、Guard、coverage gaps、可利用性和人工复核。

### AI observation

查看：分析轨道、L1 triage、candidate verdict、stop reason、cache、Prompt/Schema 版本/hash。轨道可能显示 `finalization`，同时保留 `source_analysis_track`；它不是独立的最终裁决阶段。AI observation 不覆盖确定性 Source、Sink、Guard、授权、数据流、evidence decision 或人工 review。

### Pending gaps

Gap 代表尚未覆盖的文件、方法、规则、operation、上下文或服务状态。它既可能阻止漏洞确认，也可能阻止误报/安全结论。

## 6. 人工复核

- `pending_ai`：所需自动流程未完成；
- `pending_manual`：可以开始人工判断；
- `ai_false_positive`：AI 反驳且有确定性依据，仍可人工推翻；
- `confirmed`：人工确认静态漏洞；
- `manual_false_positive`：人工确认误报。

确认漏洞或标记人工误报必须填写判断依据。当前 UI 每次提交同时发送当前状态作为 `expected_status` 和随机 `request_id`；若收到 409，会刷新 finding 并要求重新确认，避免覆盖并发更新。旧 review 值只做显示/交互兼容，不证明其历史来源。人工确认不会自动证明真实设备上的动态影响。

## 7. 预算、并发和 cache

v2 有输入/输出 token、候选逻辑调用数、扩片数、单候选墙钟、单 run 逻辑调用量和 context 体积预算。输入 token 当前是按 UTF-8 字节估算的近似值，不是 provider tokenizer 精确计费；preflight、格式 repair 和 transport retry 可能使实际 HTTP 请求数多于逻辑调用计数。候选采用有界并发；provider 有共享限流。Cache 命中表示复用了完全匹配 Prompt/Schema/输入 identity 的严格结果，不表示漏洞结论。

## 8. 常见问题

### 为什么有 L1 没有 AI 结果？

v2 不会全量发送 L1。低风险、强保护、辅助、不可达或超过 Top-N 预算的候选会跳过或 deferred。

### 为什么 AI 说“不成立”，状态仍待人工？

AI 否定意见不能单独判误报。缺少确定性反驳依据，或 negative-proof coverage 不完整时，必须保持 pending。

### 为什么 semantic closed 仍是 pending？

闭链只解决语义连接；授权、Guard、事实完整性、critical gap 或动态前置条件仍可能阻止定级。

### 为什么 AI 阶段 partial？

检查 preflight、failed/incomplete 数、stop reason、预算、provider 限流和 coverage domain。单候选失败不应抹掉其他候选结果。

## 9. 清理

- `prune_intermediates`：保留 finding/报告，删除大体积中间产物；
- `clear_sensitive_content`：删除源码、Manifest、切片等敏感内容；
- `delete_run`：完整删除，需要显式确认。

这些单 run 操作不会删除共享 AI cache。共享 cache 位于 run 目录之外，只能通过独立的显式确认管理操作清理；当前 Web cleanup 面板/API 没有共享 cache 模式。外部 provider 已接收的数据不受本地 cleanup 控制，应同时遵循 provider 的保留策略。
