# 07 - 开发指南

## 1. 开发边界

Pipeline v2 的核心原则：

- 规则、evidence validator 和 decision engine 产生/裁决确定性事实与正式状态；
- AI 只产生 strict observation；L1/L2/finalization/repair 输出都不能直接写 dataflow、Guard、授权、evidence decision 或最终 review；
- funnel、analysis、evidence、review 四层状态不能混写；
- coverage gap 同时约束正向与负向结论；
- 任何新增字段都要考虑 v1 run 的可选字段兼容。

## 2. 常用命令

```bash
# 前端
cd frontend
npm run build

# 后端测试
cd backend
pytest tests/ -v

# 全量检查
scripts/check-all.sh
```

不要用固定的历史测试数量判断成功；以当前命令退出码和实际收集数量为准。

## 4. 修改 Prompt

Prompt 是独立受控文件：

```text
prompts/
  registry.yaml
  l1-triage/<version>/system.md
  l1-triage/<version>/user.md
  l2-review/<version>/system.md
  l2-review/<version>/user.md
  ...
```

规则：

1. 新语义使用新版本目录，不覆盖已发布版本；
2. `registry.yaml` 使用精确 ID/version，不允许隐式 latest；
3. system 模板不得含 placeholder；user 模板只能含 registry 声明的规范 JSON placeholder；
4. 更新 template SHA-256；
5. 输入/输出 Schema 必须与 strict Pydantic model 字节级一致；
6. 更新 Schema SHA-256；
7. 运行 Prompt registry、AI model 和 runtime 测试；
8. 用黄金集比较指标与状态分布。

Prompt hash、rendered hash、input/output Schema hash 和版本必须进入 trace/cache descriptor。Hash 变化必须使旧 cache 失效。

## 5. 修改 Strict AI Schema

- 模型默认 `extra=forbid`、strict；
- 新字段需要更新 Pydantic model、生成的 JSON Schema、registry hash、fixture、cache descriptor 和文档；
- 不允许在解析器中补造缺失语义字段；
- 不允许把自由文本 AI 结论直接写入确定性事实；
- L1/L2/repair/finalization 使用独立输入输出协议；finalization 的 `review_recommendation` 仍是建议，适配器不得写 `review_status`。

Prompt/Schema 修改必须作为一次同步变更完成：新版本模板与 Pydantic 模型 → 生成规范 Schema → 更新 registry 模型名、文件与四类 hash → 更新 fixture/cache/trace identity → 运行 registry/runtime/黄金集测试。只改其中一项会在加载时被拒绝，不应通过关闭 hash/Schema 校验绕过。

## 6. 修改 Funnel 或 Decision

必须保持：

- exact identity 才能去重；
- AI 结果只在 deterministic fact hash 一致时传播；
- L1 `exposure_only` 保留暴露事实；
- `promotion_recommended=false` 不是误报条件；
- AI false positive 需要 AI refutation + deterministic basis；
- `ai_budget_deferred` 是预算状态，不是 evidence decision；
- 聚合不能跨候选补链。

### 规则边界回归不变量

涉及规则、索引或 dataflow 时，至少回归以下第一批边界：精确生命周期签名；framework receiver-aware taxonomy；动态 Receiver overload/flags/permission/action；Binder concrete transaction 与 reply 实参绑定；Provider 有效 overload 与 query 返回敏感性；Guard 对 Sink 的确定性 dominance；separator-aware canonical boundary；语义集合规范化且传播链保持有序的 chain identity。任何无法证明的边界必须 fail closed 为 gap/L1/不报告，不能调用 AI 填空。

## 7. Context budget 与并发

新增上下文能力时必须同时核对：

- `max_input_tokens` / `max_output_tokens`；输入估算当前为规范 JSON UTF-8 bytes `/4` 向上取整，测试不能假设特定 provider tokenizer；
- 单候选逻辑分析调用、扩片和墙钟；
- 单 run 逻辑分析调用总数；preflight、strict repair 和 transport retry 是额外实际 HTTP 行为，不与该计数一一对应；
- context 数、字节、行数；
- candidate concurrency、HTTP concurrency、provider max-in-flight；
- stop reason、coverage gap、trace 和恢复行为。

不要恢复“无限扩片”或固定串行实现。

## 8. Cache 与 Trace

Cache key 必须覆盖会改变语义的全部输入：provider/model、analysis track、Prompt version/hash、input/output Schema hash、规范候选与上下文。读取 cache 后仍需 strict 校验。

Trace 应记录候选、round、request/result 分类、stop reason、cache hit、接受响应 hash 和预算状态；不得记录密钥，也不得默认记录未脱敏原始模型正文。

共享 AI cache 位于 data root 的 `ai-cache/`，不属于任一 run。`prune_intermediates`、`clear_sensitive_content`、`delete_run` 都不得隐式删除它；共享 cache 清理必须走独立方法并显式确认，新增 HTTP 管理端点前还需单独设计权限/确认边界。

## 9. Coverage domain

新增 gap producer 时输出：

- `code`、`message`；
- `scope` 和可映射 `domain`；
- `claim_impact`；
- `critical`。

没有候选 domain 的全局 negative-proof gap 不应复制到每个 finding。测试正向证明和负向证明两种影响。

## 10. API 与前端兼容

- `pipeline_version`、`schema_version`、Prompt/Schema 元数据为可选消费；
- 前端未知 stage 使用通用渲染；
- 历史 review 值只兼容显示，不擅自重写；
- API 配置快照当前只暴露 enabled、allow_external_code、协议级 provider_kind、model；provider_kind 不是具体供应商身份，历史缺失时显示“未记录”；
- finding API 当前不保证 provider/model 顶层字段，缺失时显示“未记录”，不要猜测；
- `ai_analysis` stage 当前未汇总 cache/统一 stop/L1-L2 分轨，UI 对缺失值显示“未汇总”或不展示；selected/deferred 从 funnel 读取；
- UI 对旧 review 值只做兼容映射；当前 review 提交必须发送 status/reason，并使用 expected_status/request_id 做乐观并发与幂等，409 后刷新重试；
- 禁止向前端发送 `base_url` 原文、API key 或 secret 环境变量值；
- UI 必须把 semantic closed、AI completed/finalization 与漏洞成立分开。

## 11. Repository 迁移

目标迁移包含 run/finding 版本列、历史 review 映射、review history、幂等 request ID 和 expected-status 乐观并发。

当前代码已有版本化迁移和 review API 支撑，但仍属于并行整合/需验收项。合并或发布前必须验证：

1. 空库初始化；
2. v1 历史库升级；
3. 重复执行幂等；
4. 人工 confirmed/manual false positive 不丢失；
5. 无法证明来源的旧 false positive 不被猜测迁移；
6. 数据库列与 payload JSON 一致；
7. 失败可回滚；
8. API 并发冲突返回明确错误。

## 12. 黄金集门禁

版本化数据集位于 `evaluation/golden/v1/`，离线 runner 计算 precision、recall、F1、known-positive recall 等指标。

```bash
cd backend
python -m app.evaluation.runner --results <case-result-json>
```

开发门禁要求：

- 所有 case 有结果，无缺失 case；
- 已知高风险正例 recall 不下降；
- 已知负例不得新增无依据升级；
- Prompt/Schema fixture 全部 strict 通过；
- 状态机、coverage 和预算回归通过；
- 性能/并发基线无不可解释退化。

当前 runner 和指标已实现；自动化发布阈值/CI 阻断策略仍需项目验收和明确阈值后才能声称“自动门禁已上线”。在此之前，评测报告是必须审阅的发布证据。
