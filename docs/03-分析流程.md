# 03 - 分析流程

## 1. v2 流程

```text
规则事实
→ 确定性 guard 验证（funnel 前置步骤，非独立 stage）
→ candidate funnel
→ exact identity dedupe
→ L1 deterministic routing / AI triage
→ L2 semantic review
→ evidence integrity + decision
→ conservative aggregation
→ manual review
```

对应 run stage（manifest 正式 stage 共 11 个）：

```text
basic_check → decompiling → rule_prescan
→ 确定性 guard 验证（非独立 stage，当前 guard：debuggable）
→ api_surface → attack_surface（同一门控 api_surface.enabled，默认关闭）
→ explorer（explorer.enabled 门控，默认关闭）
→ candidate_funnel → code_slicing → ai_analysis
→ evidence_integrity_validation → aggregation
```

探索轨 validated 候选并入规则候选同走 funnel；未通过校验的探索候选 0 条进入正式 finding（留在 `explorer/candidates.json`）。

## 2. 基础检查、反编译与索引

### `basic_check`

校验 APK/ZIP 结构、大小、条目数、声明解压总量和路径穿越。失败时终止任务。

### `decompiling`

调用 JADX，提取 Manifest、资源和伪源码。部分反编译失败可进入 `partial` 并继续；缺失范围形成 coverage gap，不能把“未发现”解释为安全。

### 代码索引

索引保存类、方法、descriptor、行范围、调用边、call site、flow IR 和解析状态。热点查询使用 SQLite 索引和批量加载；规则只读访问共享索引。

## 3. `rule_prescan`

规则在受限子进程中并发执行，输出确定性候选事实：组件、位置、Source/Sink、授权、Guard、可达性和初始证据等级。

规则结果不是最终漏洞结论。规则失败或 coverage domain 缺失必须被记录。

Sink 分类数据源为 `rules/sink_taxonomy/versions.yaml`（单一事实源，当前 taxonomy_version `1.0.6`，82 条 = base 73 + manual 9）。base 为自规则实现提炼的种子条目，manual 为人工扩展条目；同名同约束冲突时 manual 覆盖 base。后端 `sink_taxonomy.py` 据此做 `custom_sink_proposal` 判定；人工确认后经 `scripts/promote_custom_sink.py` 追加为 manual 条目并递增版本（幂等：同名同约束已存在则跳过，base 条目同名同约束时升级为 manual），形成提议—确认闭环。

## 4. `api_surface` 与 `attack_surface`（默认关闭）

两个 stage 相邻执行（rule_prescan 之后、funnel 之前），共用 `api_surface.enabled` 门控（默认关闭）：

- `api_surface` 生成 API 入口表 `api-surface/api_entry_table.json`（schema：`schemas/api_entry_table.schema.json`）。入口三类来源：Binder、动态注册 Receiver、WebView JSBridge；
- `attack_surface` 生成四组件攻击面 `attack_surface/{activity,service,provider,receiver}.json`（schema：`schemas/attack_surface.schema.json`），receiver 合并 manifest 静态注册与动态注册事实。

产物服务于探索轨目标组件引导：探索轮次将命中组件的攻击面条目注入探索输入，作为“从攻击面出发”的确定性引导。门控关闭时两个 stage 跳过；此时探索轨若开启，攻击面注入降级为空，探索仍可运行。

## 5. `candidate_funnel`

funnel 输入除 rule_prescan 候选外，还包含探索轨 validated 归一化候选（与规则候选同走本节路由）。

funnel 之前先执行一步确定性 guard 验证（非独立 stage）：对全部候选检测前置 guard（当前仅 `debuggable`，依赖源码索引与 manifest 事实）。命中时写入 `guard_blocks` 证据与 `guard_blocked` 标志：候选不送 AI（源头消除），decision 阶段判 `blocked`——语义是“条件不可利用”，不是误报。

处理顺序：

1. 计算确定性 risk score 和 funnel disposition；
2. 生成 `scope_key`、`chain_key`、`deterministic_fact_hash`；
3. 仅对三个 identity 完全相同的候选精确去重；
4. 为每组选择一个 AI representative，保留成员 provenance；
5. L2 代表项进入 review；
6. 高风险 L1 按 `max_l1_candidates_per_run` 和最低 risk score 选择；
7. 超出预算的 L1 标记 `ai_budget_deferred`。

`selected` 表示进入本次 AI 工作清单；`deferred` 表示预算延后，绝不等价于误报。

funnel 之后执行同链关联回填（`link_related_candidates`）：探索归一化候选与规则候选同链时双向写 `related_candidate_ids`（幂等；`related` 字段不参与三重身份判定，回填不影响去重结果）。

## 6. `code_slicing`

围绕组件入口、Source、Sink、Guard 和传播关系生成方法级切片。扩片目标使用 canonical method target，并按严格顺序解析；多目标歧义不能任选。

显式预算包括：

- 单请求输入/输出 token；输入 token 当前按规范 JSON 的 UTF-8 字节数 `/4` 向上取整近似，不能当作 provider tokenizer 的精确计费；
- 单候选逻辑分析调用数与扩片数；
- 单候选墙钟；
- 单 run 逻辑分析调用数；preflight、strict repair 和 transport retry 可能使实际 HTTP 请求数更多；
- context 数、字节、行数和单次新增数。

达到预算产生 stop reason，例如 `expansion_budget_finalized`、`expansion_budget_exhausted`、`context_expansion_stalled`。因此旧描述“无 token 预算、无限自然扩片”已废弃。

## 7. `ai_analysis`

### Preflight

先发送不含 APK 代码的连通性/鉴权检查。全局不可恢复错误可打开任务断路器；单候选格式或上下文错误不应熔断整个 run。

### L1 triage

不是全部 L1 都进入 AI。只处理 funnel selected 的高风险代表项。

| `triage_disposition` | 语义 |
|---|---|
| `potential_chain` | AI 观察到潜在链，必须经过确定性验证 |
| `exposure_only` | 外部暴露事实成立，当前覆盖内未形成敏感链 |
| `insufficient` | 上下文不足，保留 pending gap |

`exposure_only` 不否定 exported/permission 等事实；不能自动标记误报。

### L2 review

AI 对已有静态链做语义复核，输出 `analysis_track`、`candidate_verdict`、证据引用、context requests 和 observation。Source、Sink、Guard、授权和数据流仍由确定性代码裁决。

条件分支：`verify.enabled`（默认关闭）时，单轮 L2 被 VerifyAgent 多轮核验替代——仅 L2 候选进入核验（L1 不进核验），按轮次取证与读码；核验失败或预算耗尽时按 `fallback_to_single_turn_l2` 回退单轮 L2，主链不阻塞。

### Finalization observation

扩片到达上限或没有新上下文时，编排层可用单独的 finalization Prompt 要求模型基于已有材料收尾。输出中的 verdict 与 `review_recommendation` 只保存在 AI 分析轨道中，不直接写 `review_status`，也不决定 dataflow、Guard、authorization、evidence decision 或 severity。

### 其他 AI 调用面

Prompt registry 共 9 个 prompt ID：`preflight`、`l1-triage`、`l2-review`、`finalization`、`repair`、`explorer`、`explorer-deep-dive`、`verify`、`report`。除前述流水线内调用面外：

- `explorer` / `explorer-deep-dive`：探索轨检索循环与 partial 候选深挖，深挖请求计入独立的 deep_dive 账本；
- `verify`：多轮核验，见上文 L2 review 条件分支；
- `report`：finding 报告草稿，由 API 按需触发（`POST /api/findings/{finding_id}/report-draft`），不属于流水线 stage。

### Strict response

Prompt registry 按精确 ID/version 加载独立 `system.md`/`user.md`；输入和输出均由 strict Pydantic/JSON Schema 校验。额外字段、错误枚举、Schema/hash 不一致都会被拒绝。解析失败只允许受控格式 repair，不补造语义字段。修改 Prompt 或模型时必须同步更新版本目录、Pydantic model、生成 Schema、registry template/Schema hash、fixture 与 cache/trace identity，否则加载失败。

### 并发、cache、trace

候选采用有界并发；provider 共享在途请求和冷却控制。Cache key 包含 provider/model、Prompt/Schema hash、分析轨道和规范输入。命中 cache 仍记录 `cache_hit`；每候选增量记录 trace、stop reason 和接受的响应 hash。

## 8. `evidence_integrity_validation` 与 decision

### 三个正交状态

| 字段 | 典型值 | 说明 |
|---|---|---|
| `fact_integrity_status` | verified/incomplete/invalid | 引用事实是否可回查 |
| `semantic_status` | closed/not_proven/not_applicable | Source→Sink 语义链是否闭合 |
| `exploitability_status` | statically_gradeable/dynamically_confirmed/pending | 是否满足定级条件 |

`semantic_status=closed` 不等于漏洞成立。若强授权、有效 Guard、critical gap 或事实不完整，仍可能 `exploitability_status=pending`。

### `evidence_decision`

常见值：

- `supported`
- `unresolved`
- `exposure_only`
- `deterministically_refuted`
- `ai_false_positive`
- `blocked`（确定性 guard 阻断，如 release 包被 debuggable guard 拦死——语义是“条件不可利用”，不是误报，区别于 `deterministically_refuted`）
- `ai_likely_supported` / `ai_likely_false_positive`（联合裁决 v1 的倾向性分档：AI 中成立或倾向否定但无确定性反证背书。两者都不是终态，需人工确认；`ai_likely_false_positive` 映射 review_status=`pending_manual`，reason=`ai_likely_false_positive_needs_confirmation`）
- 聚合后可能为 `mixed`

AI 否定意见只有同时具备确定性反驳依据，才允许 decision engine 形成 `ai_false_positive`；AI 否定而无确定性反证时只形成 `ai_likely_false_positive`（倾向性，保留候选待人工确认）。`promotion_recommended=false`、finalization 的 `review_recommendation` 或 AI verdict 单独出现时都不等于误报或最终决定。

### Coverage domain

Gap 记录作用域和 claim impact。缺口既可阻止正向漏洞证明，也可阻止负向“安全/误报”证明。前端将其显示为 pending gap。

## 9. `aggregation`

聚合保留代表项与成员 provenance，不跨候选拼接证据链。聚合 review 采用保守优先级：已确认人工结论保留；任一成员仍需 AI 时保持 `pending_ai`；只有全部成员满足反驳条件时才可聚合为 AI false positive。

## 10. Review 状态

| 状态 | 含义 |
|---|---|
| `pending_ai` | 所需 AI/证据流程未完成 |
| `pending_manual` | 自动流程完成，等待人工判断 |
| `ai_false_positive` | AI 反驳且已有确定性依据；可被人工推翻 |
| `manual_false_positive` | 人工确认误报 |
| `confirmed` | 人工确认静态漏洞结论 |

人工 `confirmed` 不能自动写成动态可利用。人工确认和人工误报必须填写理由。

联合裁决 v1 引入的 `ai_likely_false_positive`（及 `ai_likely_supported`）是上游证据态，不是新的终态：终态集合仍为表中 5 值。`ai_likely_false_positive` 映射为 `pending_manual`（reason=`ai_likely_false_positive_needs_confirmation`），前端仅按 review_status 展示（显示为“待人工复核”），倾向性信息保存在 reason 与 evidence_decision 字段中。

## 11. 已废弃语义

以下描述不再适用于 v2：

- “全部 L1 发送给 AI”；
- “`promotion_recommended=false` 就是误报”；
- “无 token/请求/墙钟预算”；
- “AI 固定串行执行”；
- “AI 服务成功等于证据闭环或漏洞成立”；
- “semantic closed 等于漏洞成立”。
