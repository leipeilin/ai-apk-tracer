# 08 - Pipeline v2：L1 AI 分诊与语义复核权威设计

## 1. 文档地位

本文是 pipeline v2 的权威设计和实施状态说明。实际运行仍以当前代码、Schema、Prompt registry 和测试结果为准；“设计完成”不等于所有迁移与发布门禁已验收。

## 2. 核心原则

1. AI 只产生 strict observation：L1 triage、L2 review、repair、finalization 都不负责确定性 dataflow、Guard、authorization、evidence decision、severity 或最终 review。
2. L1 exposure 是攻击面事实，不是漏洞声明。
3. 不把全部 L1 发送给 AI，只选择高风险代表项。
4. L1→L2 必须经过确定性 Source/Sink/路径/授权验证。
5. `promotion_recommended=false`、`exposure_only` 或“未找到链”不能单独判误报。
6. 语义闭链不等于漏洞成立。
7. Gap 同时可能阻止正向漏洞证明和负向安全证明。
8. 所有 Prompt、Schema、预算、cache 和 trace 都必须版本化、可审计。
9. AI 默认开启且允许外发代码切片；UI/文档必须显式提示隐私边界。

## 3. 正式流程

```text
rule_prescan
→ deterministic precheck
→ candidate identity
→ exact dedupe
→ L1 risk budget selection / L2 representative routing
→ context budgeted slicing
→ AI preflight
→ L1 triage
→ deterministic promotion validation
→ L2 review
→ optional finalization observation
→ evidence integrity
→ decision engine
→ conservative aggregation
→ manual review
```

Manifest stage：

```text
basic_check → decompiling → rule_prescan → candidate_funnel
→ code_slicing → ai_analysis → evidence_integrity_validation → aggregation
```

## 4. Candidate funnel

### 4.1 Identity

AI 结果复用必须同时匹配：

- `scope_key`
- `chain_key`
- `deterministic_fact_hash`

仅规则 ID、标题或相似组件名相同不能去重。语义集合字段可规范排序，但 `propagation_paths` 等链路字段保持顺序，反转路径必须形成不同 `chain_key`。代表项必须保留 `member_candidate_ids`、`representative_candidate_id` 和 evidence variants。

### 4.2 Disposition

- `deterministically_refuted`
- `exposure_only`
- `deterministically_promoted_l2`
- `high_risk_uncertain`
- `coverage_insufficient`

### 4.3 L1 budget

L1 根据 risk score 和 review priority 排序，受 `min_l1_risk_score` 与 `max_l1_candidates_per_run` 约束。

- selected：进入本次 triage；
- deferred：`analysis_status=ai_budget_deferred`，保留事实与待处理状态；
- deferred 不得映射为 false positive。

## 5. L1 triage

### 5.1 输入

- Manifest/动态注册 exposure；动态 Receiver 输入包含已解析的 API family/overload、flags、permission、actions、protected-action catalog、外部可达性与 coverage gap；
- operation 级授权事实；
- 组件入口方法；
- 受预算限制的代码上下文；
- 已知 Guard 和 coverage domain。

### 5.2 Strict 输出

`triage_disposition`：

| 值 | 语义 | 后续 |
|---|---|---|
| `potential_chain` | AI 观察到潜在 Source/Sink/路径 | 进入确定性 promotion 校验 |
| `exposure_only` | 暴露成立，当前覆盖内无敏感链 | 保留 L1，通常待人工 |
| `insufficient` | 上下文不足 | pending AI/gap |

AI 建议必须引用真实 context/path/line。建议写入 AI proposal/observation，不能直接覆盖正式 `sources`、`sinks`、`propagation_paths`。

### 5.3 Promotion 门禁

至少校验：

- Source taxonomy；
- receiver/type-aware Sink taxonomy；
- entry→source→propagation→sink 每一跳；
- operation 级授权；
- Guard 是否有效支配 Sink；
- 同一候选，不跨候选拼链；
- 无阻断该结论的 critical gap。

只有规范化确定性事实可以写入 L2。动态 Receiver 特别遵循：仅注册暴露时输出 L1；只有注册点→解析出的 Receiver 类型→精确 `onReceive(Context, Intent)`→已验证副作用闭合且没有 critical gap 时输出 L2。

## 6. L2 review

L2 AI 可解释静态链、给出 Guard observation、提出精确扩片请求和 candidate verdict，但不确认 Guard 是否有效。扩片到限或停滞时 finalization 可给出 verdict/review recommendation；适配器保留原分析轨道并且不写 `review_status`。确定性系统继续负责：

- 证据引用回查；
- Source/Sink 分类；
- dataflow/调用边；
- 授权和 Guard；
- evidence decision；
- severity/exploitability 门禁。

### 6.1 第一批确定性规则不变量

当前回归基线覆盖：

1. 生命周期名称与参数签名必须精确，同名 overload 不作为入口；
2. taxonomy 必须结合可信 framework receiver type/descriptor，应用类同叶子名不能冒充 Android API；
3. 动态 Receiver 联合 overload、flags、permission、action/protected catalog 判断；未知表达式 fail closed；
4. Binder 必须绑定 concrete transaction/case/implementation，reply 泄露必须证明 `write*` 实参来自该 dispatch 结果；
5. Provider 只分析有效生命周期 overload，query 敏感性来自实际选择列/返回证据而不是方法全文关键词；
6. Guard 必须在同一 transaction/路径确定性支配 Sink，无法证明 dominance 时保留 critical gap；
7. 文件/URI 使用 separator-aware canonical boundary，并联合 paths/authority/grant/permission；
8. chain identity 对集合字段规范化、对传播路径保序，仅完整 identity 相同才去重/传播。

这些边界不能委托 AI 补全；证据不足时保持 L1/unresolved/gap 或不报告。

## 7. Prompt registry 与 Strict Schema

Prompt 独立存放：

```text
prompts/<prompt-id>/<semver>/system.md
prompts/<prompt-id>/<semver>/user.md
prompts/registry.yaml
```

Registry 固定：Prompt ID/version、模板文件、唯一 JSON placeholder、input/output model、Schema 文件、template hash、Schema hash。

加载时必须：

- 拒绝重复 YAML key、symlink 和越界路径；
- 校验 UTF-8、文件大小和 SHA-256；
- 校验模板 placeholder；
- 校验 Schema 与 strict Pydantic model 字节级一致；
- 不存在版本时拒绝，不隐式回退。

Trace/report/cache descriptor 记录 Prompt version/hash 与 input/output Schema hash/version。

变更必须同步完成：创建新 Prompt 版本目录、更新 strict Pydantic input/output model、重新生成规范 Schema、更新 registry 文件/模型名/template hash/Schema hash、更新 fixture 与 cache/trace identity，再运行 registry/runtime/黄金集测试。任何一处不同步都会拒绝加载；不得把 hash 或 Schema 检查降级成 warning。

## 8. 上下文预算与停止语义

v2 有明确预算，不再使用“无 token 预算”模型：

- `max_input_tokens`、`max_output_tokens`；输入 token 当前按规范 JSON 的 UTF-8 bytes `/4` 向上取整近似，不是 provider tokenizer 精确值；
- `max_requests_per_candidate`；
- `max_expansions_per_candidate`；
- `max_candidate_wall_seconds`；
- `max_requests_per_run`；候选/run 预算按编排层 triage/review/finalization 逻辑调用计数，preflight、strict repair 和 transport retry 可能产生额外实际 HTTP 请求；
- context 数、字节、行数和单次新增限制。

Stop reason 必须可见，例如：

- `analysis_complete`
- `analysis_incomplete_no_requests`
- `expansion_budget_finalized`
- `expansion_budget_exhausted`
- `expansion_stalled_finalized`
- `context_expansion_stalled`
- `ai_failed` / `ai_skipped`

停止原因描述执行边界，不直接决定漏洞或误报。

## 9. 并发、Provider 控制、Cache 和恢复

- 候选采用有界并发，不固定串行；
- 进程级 HTTP 并发与 provider 最大在途请求分开控制；
- provider controller 处理共享 Retry-After/冷却；
- 任务 circuit 只处理全局错误；单候选错误局部隔离；
- Cache 内容寻址且包含 provider/model、track、Prompt/Schema hash 和规范输入；
- Cache 读取后重新 strict 校验；
- 增量 trace/checkpoint 支持中断后识别已完成工作；
- 共享 cache 位于所有 run 之外，任何单 run cleanup 都不删除；只有独立管理调用加显式确认才可清空。

当前 UI/API 的真实边界：`ai_analysis` stage summary 提供 preflight、analyzed/completed/failed/skipped/incomplete 和可选 circuit reason；正常进入候选调度时还提供 peak concurrency，无候选、无 context 或 preflight 失败的早退路径缺失该字段时显示“未汇总”。该 summary 不汇总 cache、统一 stop reason 或 L1/L2 分轨，前端不得猜测；selected/deferred 来自 funnel。

## 10. Coverage domain

Gap 结构包含：

```text
code, message, scope, domain,
claim_impact, affects_positive_proof,
affects_negative_proof, critical
```

Domain 可定位 file/class/method/component/rule/operation。只有与候选 domain 匹配的 gap 才传播到候选；全局 negative-proof gap 保留在 run 级。

## 11. 状态语义

### 11.1 四层状态

| 层 | 字段 | 例子 |
|---|---|---|
| Funnel | `funnel_disposition` | exposure_only/high_risk_uncertain |
| Analysis | `analysis_status` | ai_completed/ai_incomplete/ai_budget_deferred |
| Evidence | `evidence_decision` | supported/unresolved/deterministically_refuted |
| Review | `review_status` | pending_ai/pending_manual/confirmed |

### 11.2 事实、语义、可利用性

- `fact_integrity_status=verified`：引用事实有效，不代表漏洞。
- `semantic_status=closed`：静态链闭合，不代表授权/Guard/coverage 门禁通过。
- `exploitability_status=statically_gradeable`：满足静态定级条件，仍不等于动态利用已验证。
- `dynamically_confirmed` 必须来自独立动态证据。

### 11.3 Review

- `pending_ai`
- `pending_manual`
- `ai_false_positive`
- `manual_false_positive`
- `confirmed`

AI false positive 必须同时有 AI refutation 和 deterministic basis。人工 confirmed/manual false positive 必须记录理由；人工确认不修改动态验证状态。当前 review API 接受 `status`、`reason`、`expected_status`、`request_id`（另有 actor/basis），UI 已发送前四项并在 409 后刷新。旧 `pending`/`false_positive`/`ai_candidate` 只做显示与交互映射，不据此猜测历史来源。

## 12. AI 外发与隐私

默认保持 `enabled=true`、`allow_external_code=true`，因此 selected 候选的方法级代码切片可外发。

必须满足：

- 前端显著显示默认行为和本 run 快照；
- run API 当前只返回 enabled/allow_external_code/协议级 provider_kind/model；`openai-compatible` 不是具体供应商身份，历史 run 或 finding provider/model 缺失时显示“未记录”；
- 显示 model/AI 阶段状态，但不把协议兜底冒充供应商审计字段；
- 不显示 `base_url` 原文或密钥；
- trace/log 不记录密钥或默认保存未脱敏原始正文；
- 本地 cleanup 不代表 provider 侧数据已删除。

## 13. 兼容与迁移

### 13.1 版本

- run/finding：`pipeline_version`、`schema_version`；
- manifest：`artifact_schema_versions`；
- AI：Prompt/Schema version/hash；
- v1 缺失字段按可选字段读取。

### 13.2 Review migration

迁移需版本化、幂等、可回滚，并区分人工审计来源。不能把全部旧 `pending` 统一映射为 pending_manual，也不能把来源不明的旧 false positive 猜成 AI 或人工结论。

当前 repository migration、review history/幂等/乐观并发相关代码已实现并有针对性测试，但处于并行整合与全量验收阶段。发布前仍需历史数据库抽样、重复迁移、失败回滚、payload/列一致性和并发冲突验收。

## 14. 黄金集门禁

已实现：

- `evaluation/golden/v1` 版本化数据集；
- strict loader；
- precision、recall、F1、known-positive recall 等离线指标；
- AI response strict fixture；
- runner JSON 报告。

发布要求：无缺失 case、已知正例 recall 不下降、已知负例不新增无依据 promotion、Prompt/Schema fixture 全通过、状态/coverage/预算/性能回归通过。

当前自动化发布阈值仍需明确和验收，因此只能声称“黄金集与指标 runner 已实现”；在 CI 阈值真正阻断发布前，不声称自动门禁已完全上线。

## 16. 明确废弃的旧描述

以下说法必须从设计、UI 和评审中移除：

- 全部 L1 送 AI；
- promotion false 等于误报；
- 无 token/请求/墙钟预算；
- AI 固定串行；
- HTTP 200/AI completed 等于证据闭环；
- semantic closed 等于漏洞成立；
- 本地 cleanup 等于外部 provider 数据已删除；
- migration 代码存在就等于历史数据迁移已全面上线。
