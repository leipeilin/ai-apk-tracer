# 09 - 漏洞风险等级定义（行业标准对齐）

> **更新日期**：2026-08-09  
> **版本**：1.0.0  
> **依据**：CVSS v3.1（Base Score 定性映射）、OWASP Mobile Application Security Verification Standard (MASVS)、OWASP Mobile Top 10 (2024)、CWE Top 25、NIST SP 800-30 风险表述  
> **本项目定位**：个人本地单用户静态扫描工具，等级用于**人工复核优先级排序**，不是最终裁决——`determine_severity()` 仍为唯一定级入口，本知识库是其"为什么这么定"的判据说明与人工复核指引。

---

## 1. 等级体系总览

本项目 6 档等级（与 `backend/app/findings/severity.py` 的 `SEVERITIES` 枚举一致）：

| 等级 | 英文            | 含义（一句话）                                         | 对应 CVSS v3.1 Base 定性 | 处理要求        |
| -- | ------------- | ----------------------------------------------- | -------------------- | ----------- |
| 严重 | critical      | 无需特殊前提即可造成**远程任意代码执行/资金损失/大规模数据泄露**             | 9.0–10.0             | 立即复核，优先动态验证 |
| 高危 | high          | 可造成**敏感数据泄露/认证绕过/本地提权**，有一定前提条件                 | 7.0–8.9              | 尽快复核        |
| 中危 | medium        | 可造成**有限影响**（低敏感数据、受限操作），需用户交互或特殊前提              | 4.0–6.9              | 常规复核        |
| 低危 | low           | 影响很小（信息暴露、UI 提示），或利用门槛极高                        | 0.1–3.9              | 批量复核        |
| 提示 | informational | **攻击面/配置事实**，不构成漏洞链（L1 暴露事实、已确认 Guard 保护、已确认误报） | 0.0（无 CVSS）          | 记录归档，不要求修复  |
| 待定 | pending       | **证据不足**：关键缺口、数据流未证、授权未知、AI 未完成——不可可靠定级         | N/A（不足以评估）           | 补充证据后再定级    |

**核心原则**（与 `determine_severity()` 对齐）：等级只表示"成立后的影响与利用门槛"，必须与置信度、证据等级（L1/L2/L3）、动态验证状态**分离**。pending 不是低危，是"还没资格定级"。

## 2. 判定维度（对齐 CVSS v3.1 因子）

`determine_severity()` 消费候选的以下字段做降级保护；人工复核时按本表核对等级是否合理：

### 2.1 攻击向量（AV）→ 可达性分级

| 本项目          | CVSS AV             | 定义                 | 示例                     |
| ------------ | ------------------- | ------------------ | ---------------------- |
| remote       | N（Network）          | 任意外部应用/远程可达入口      | exported 无权限组件、深链、隐式广播 |
| local        | A/L（Adjacent/Local） | 需本地交互/本地提权前置       | 需用户点击、需 shell、需安装恶意应用  |
| supply_chain | N 但依赖链              | 依赖/插件/资源投毒         | 动态加载、不校验来源的 dex/jar    |
| device       | P（Physical）         | 设备 API 调用（需协议输出确认） | 传感器、NFC、蓝牙             |

### 2.2 影响因子（C/I/A）

- **confidentiality（保密性）**：数据泄露——高（账户/token/支付/联系人）/低（设备标识/UI 状态）/无
- **integrity（完整性）**：数据篡改——高（支付金额/权限状态）/低（偏好设置）/无
- **availability（可用性）**：拒绝服务/资源耗尽——高（服务不可用）/低（进程崩溃可恢复）/无

### 2.3 前提条件（对应 CVSS PR/UI/AC）

| 因子                        | 提级方向                    | 降级方向               |
| ------------------------- | ----------------------- | ------------------ |
| privileges_required（所需权限） | 无需权限（N）→ 提级             | 需高权限（H）→ 降级        |
| user_interaction（用户交互）    | 无需交互（N）→ 提级             | 需交互（R）→ 降级         |
| attack_complexity（攻击复杂度）  | 低（L）→ 提级                | 高（H）→ 降级           |
| scope（影响范围）               | changed（S:C，影响跨授权域）→ 提级 | unchanged（S:U）→ 常规 |

## 3. 等级判定速查表（静态阶段）

> 静态阶段**不得**凭"疑似"定级。以下判据在 `determine_severity()` 的降级保护之外，供规则 severity_hint 与人工复核参考。

### 3.1 严重（critical）——必须满足**全部**：

1. 攻击向量 remote 或 supply_chain（无需本地交互）
2. 影响至少一项为**高**（C/A/I 高）：资金损失、认证/token 泄露、RCE、支付篡改
3. 无有效 Guard/授权阻断（guard_status ≠ present_effective，authorization_status ≠ protected）
4. 数据流已证（dataflow_status ≠ not_proven）或确定性闭链（deterministic_chain_verified）
5. 无关键缺口（无 critical gap）

**典型规则**：`WEBVIEW_JS_BRIDGE_EXPOSED`（JS 桥注入→任意方法调用）、`TRUST_MANAGER_ALL_ACCEPT`（接受任意证书→全量 MITM）

### 3.2 高危（high）——满足**部分**严重条件：

1. 攻击向量 remote/local，影响至少一项**中高**
2. 数据流已证或确定性闭链
3. Guard/授权**未证明有效**（unknown/present_partial，不是已确认保护）

**典型规则**：`SERVICE_BINDER_CALLER_CHECK_MISSING`（IPC 无调用者校验→敏感操作）、`PROVIDER_URI_TO_FILE`（URI→文件系统）、`WEBVIEW_FILE_ACCESS_ENABLED`、`WEBVIEW_UNIVERSAL_ACCESS_FROM_FILE`、`WEBVIEW_SSL_ERROR_IGNORED`、`HOSTNAME_VERIFIER_ALWAYS_TRUE`、`DEBUGGABLE_IN_PRODUCTION`

### 3.3 中危（medium）——满足：

1. 攻击向量 remote/local，影响**低**或需**用户交互/特殊前提**
2. 数据流已证（至少 intraprocedural）
3. 影响为 potential 时从 high 降 medium（`determine_severity` 已实现）

**典型规则**：`ACTIVITY_INTENT_TO_SENSITIVE_SINK`、`RECEIVER_INPUT_TO_SINK`、`IMPLICIT_BROADCAST_SENSITIVE_DATA`、`CLEARTEXT_TRAFFIC_ALLOWED`、`ALLOW_BACKUP_ENABLED`、`WEAK_CIPHER_ECB`、`WEBVIEW_EXTERNAL_CONTENT`

### 3.4 低危（low）：

- 信息暴露（非敏感）、UI 提示、利用门槛极高
- 或影响仅限进程内且无外溢通道（红线 23 场景但静态可判）

### 3.5 提示（informational）——**不构成漏洞**：

- L1 攻击面事实（导出组件但无敏感 sink）
- 已确认 Guard 有效（guard_status=present_effective）
- 已确认授权保护（authorization_status=protected/strongly_protected）
- AI 误报/确定性反驳（evidence_decision=ai_false_positive/deterministically_refuted）
- SDK 标准导出组件（WXEntry/PayEntry 等）

### 3.6 待定（pending）——**无资格定级**，必须满足其一：

1. 存在 critical gap（blocking_gaps/ai_blocking_gaps/coverage_gaps 任一 critical）
2. dataflow_status=not_proven（不可信输入→敏感操作传播未证）
3. authorization_status=unknown（授权状态未知）
4. guard_status∈{unknown, present_partial}（Guard 未证明 fail-closed）
5. AI 未完成（ai_failed/ai_skipped）且无确定性闭链
6. guard 阻断（evidence_decision=blocked，当前构建不可利用）

### 4.1 OWASP Mobile Top 10 (2024) ↔ 本项目规则

| OWASP 类别                                 | 本项目规则                                                                                           |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------- |

### 4.2 CVSS v3.1 分数映射建议

| CVSS Base | 本项目等级              |
| --------- | ------------------ |
| 9.0–10.0  | critical           |

## 5. 等级与其它属性的关系（防混淆）

| 属性                 | 与等级的关系                                           |
| ------------------ | ------------------------------------------------ |
| **置信度 confidence** | 独立。高置信的 low 漏洞仍是 low；低置信的 critical 候选仍可能 pending |
| **证据等级 L1/L2/L3**  | 独立。L3 高置信链 ≠ high；L1 攻击面 ≠ 漏洞                    |
| **动态验证状态**         | 独立。未动态验证不自动降级，但影响未证实（potential）会从 high 降 medium  |
| **review_status**  | 独立。pending_manual 是队列状态不是等级                      |
| **CVSS 分数**        | 本项目不输出分数（AI 不定级铁律），仅人工复核时按需计算                    |

## 6. 人工复核等级确认清单

复核 `confirmed` 漏洞前，按此清单核对等级：

- [ ] 攻击向量：remote/local/supply_chain/device？（对齐 §2.1）
- [ ] 影响：C/I/A 各是高/低/无？（对齐 §2.2）
- [ ] 前提：需权限？需交互？复杂度？（对齐 §2.3）
- [ ] 对照 §3 速查表：等级是否匹配？
- [ ] 是否有已确认 Guard/授权应降级为 informational？
- [ ] 是否有未证明项应保持 pending？
- [ ] 如需对外报告，按 §4.2 计算 CVSS 分数并说明

## 7. 自动化接入状态（v1.0.0）

**当前状态（2026-08-09）**：本知识库为**纯参考文档，零代码引用**（已 grep 验证）。系统等级判定链路为：

```
规则层 RULE_META / severity_hint（29 条规则硬编码建议等级，informational 8 / medium 8 / high 11 / critical 2）
→ determine_severity()（aggregate.py:73 / decision.py:140 唯一入口，只做降级保护：critical gap→pending、
  dataflow not_proven→pending、guard 有效→informational、impact potential→high 降 medium；永不升级）
→ 最终 severity
```

AI 不参与定级（schema 仅有 `impact_vector` CVSS 因子描述，l2-review 3.0.5 明确禁止输出 severity_class/CVSS 分数）。

**已知缺口**：`determine_severity()` 的降级逻辑与本知识库 §3 速查表的"升级判据"（critical 需 5 条件全满足等）**没有对应实现**——规则 severity_hint=critical 且证据闭合即直接 critical，缺少按影响因子重新评估的机制。

**后续升级待办（方案 A，已建任务 #49）**：RULE_META 增加 `impact_factors`（C/I/A 等级 + 攻击向量 + 前提），determine_severity() 参照 §3 做双向判定。**前置条件**：先解决证据闭链（当前 132/260 候选 pending 的根因是 critical gap 阻断，非判据缺失）。保持 AI 不定级铁律。
