# 02 - 架构设计

## 1. Pipeline v2 总览

AI-APK-Tracer 是本地静态分析系统。APK 不会被执行；规则、索引和证据判断由确定性代码完成，AI 只提供受严格 Schema 约束的语义 observation。

```text
APK
→ basic_check
→ decompiling + index
→ rule_prescan
→ guard 验证（确定性，funnel 前步骤，非独立 stage）
→ api_surface（api_entry_table + attack_surface，同受 api_surface.enabled 门控）
→ explorer（可选探索轨，explorer.enabled 门控，默认关闭）
→ candidate_funnel（确定性预判、精确去重、预算路由）
→ code_slicing
→ ai_analysis（L1 triage / L2 review，或可选 verify 核验）
→ evidence_integrity_validation + decision
→ aggregation
→ manual review
```

当前 manifest 的正式阶段名为：

1. `basic_check`
2. `decompiling`
3. `rule_prescan`
4. `api_surface`
5. `attack_surface`
6. `explorer`
7. `candidate_funnel`
8. `code_slicing`
9. `ai_analysis`
10. `evidence_integrity_validation`
11. `aggregation`

- `api_surface` 与 `attack_surface` 同受 `api_surface.enabled` 门控（默认关闭）：`api_surface` 阶段生成 API 入口表（`schemas/api_entry_table.schema.json`），`attack_surface` 为其子阶段，生成四组件攻击面（`schemas/attack_surface.schema.json`）；门控关闭时不执行、不出现在 manifest。
- `explorer` 受 `explorer.enabled` 门控，默认关闭。
- guard 验证发生在 `rule_prescan` 之后、`candidate_funnel` 之前，由确定性代码对全部候选执行（当前仅 debuggable guard），是 funnel 前步骤而非独立 stage。

未知阶段由前端按通用阶段显示，避免新后端阶段破坏旧 UI。

## 3. Candidate funnel

Funnel 不做模糊合并。候选 identity 由作用域、顺序链和确定性事实哈希组成；只有 identity 完全相同的候选才复用代表项 AI 结果。

正式 disposition 包括：

- `deterministically_refuted`
- `exposure_only`
- `deterministically_promoted_l2`
- `high_risk_uncertain`
- `coverage_insufficient`

Funnel 同时记录原候选数、identity group 数、精确去重数、AI representative 数、L1 selected/deferred 数。`deferred` 表示预算延后，不表示误报或安全。

## 4. 规则轨与可选探索轨

AI 的职责边界在两条轨上一致：只提供受严格 Schema 约束的语义 observation，不写确定性事实。哪些候选送 AI 由确定性代码决定：funnel 前置 guard 验证命中（`guard_blocked`）的候选不送 AI；L1 默认不送；探索轨 validated 候选并入主链后与规则候选同走 funnel 路由。

### L1 triage

只选择高风险、外部可达、非辅助且未被强保护的 L1 代表候选。默认不会把全部 L1 送给 AI。

`triage_disposition`：

- `potential_chain`：值得进入确定性链验证；不是漏洞结论。
- `exposure_only`：暴露事实成立，但当前覆盖内未形成敏感链。
- `insufficient`：上下文不足。

### L2 review 与 finalization

L2 输入包含确定性 Source、Sink、传播关系、Manifest/授权事实和方法级上下文。AI 可以解释语义、提出 context request 和候选 verdict，但不能覆盖确定性事实。扩片达到上限或停滞时可能调用独立 finalization Prompt；其 `verdict`/`review_recommendation` 仍只是 observation，编排层不会直接把它写成 `review_status`，最终状态由 evidence validator、decision engine 与人工复核产生。

### 核验替代路径（verify）

`verify.enabled`（默认关闭）时，`VerifyAgent` 多轮核验替代单轮 L2：命题清单由确定性代码从候选事实生成（不从提出者描述生成），盲验输入只含可回查事实层，终止条件由代码判定而非模型自声明。核验仅覆盖 L2 候选（L1 不进）；失败或预算耗尽按 `fallback_to_single_turn_l2` 回退现有单轮 L2，主链不阻塞。输出对齐 L2 关键决策字段，DecisionEngine 消费方式不变——核验结论仍只是 observation。

### 可选探索轨（explorer）

`explorer.enabled`（默认关闭）时启用探索轨：检索循环 → 三档校验 → 深挖（deep dive）。通过校验的（validated）探索候选归一化为正式候选并入主链，与规则候选同走 funnel 路由与 L2 复核；partial/unverified 留在 `explorer/candidates.json` 与人工队列，不进入正式 finding。入口并行度有界；目标组件引导（规则轨 finding 组件入口优先 + known_findings 注入）只影响探索顺序，不改变覆盖口径；探索候选实时落盘。深挖只为 partial 候选补齐可回查证据，不改链、不升级。

### 报告草稿（report）

AI 报告草稿不是流水线阶段：由 API 按需触发（`POST /api/findings/{finding_id}/report-draft`），仅 confirmed finding 可触发。AI 草稿与确定性证据分离——evidence_refs 由确定性投影补齐，AI 失败或输出不符合严格契约时降级回确定性投影，报告生成不因 AI 阻塞；可执行 PoC 默认禁止（仅骨架）。

### Strict protocol

- Prompt 位于独立版本目录，不嵌入 Python 字符串。
- `prompts/registry.yaml` 固定 Prompt ID/version、输入/输出模型、Schema 文件和 SHA-256。
- 注册 9 个 Prompt ID：`preflight`、`l1-triage`、`l2-review`、`finalization`、`repair`、`explorer`、`explorer-deep-dive`、`verify`、`report`；对应 `ai.py` 调用面 preflight / triage_l1 / review_l2 / finalize / explore_entry / deep_dive_entry / verify_entry / report_entry 与输出格式 repair。
- Pydantic 模型使用 strict/extra-forbid 语义。
- Prompt/Schema hash 不匹配时拒绝加载，不隐式回退版本。
- 接受的结果记录 Prompt 版本、Schema 版本/hash、stop reason、cache 状态和 trace 元数据。

## 5. 预算、并发、缓存与 trace

v2 已有显式边界：

- 单请求输入/输出 token 预算；输入 token 当前以规范 JSON 的 UTF-8 字节数除以 4 向上取整近似，不是 provider tokenizer 的精确计费值；
- 单候选请求数、扩片数、墙钟和 context 数/字节/行数预算；
- 单 run 读码请求总量预算（`context_budget.max_requests_per_run`）：`None` = 无上限；当前 `config/default.yaml` 配置为 `null`，是 T1 验证期临时值，验证完成后须回归定参。该预算为全轨共享池，统一短路 L1/L2、explorer、deep dive、verify 四处调用点，短路产生 `run_request_budget_exhausted` stop reason；编排层按逻辑调用计数，preflight、格式 repair 和 transport retry 可能产生额外实际 HTTP 请求，因此该数字不是 provider 账单请求数；
- run 级请求账本分 4 本：主 AI、explorer、deep dive、verify 分账计数，汇总进 `ai_analysis` stage summary（见 §9）；
- 候选级并发、进程级 HTTP 并发、provider 最大在途请求；
- Retry-After/冷却和任务断路器；
- 内容寻址本地 cache；
- 候选增量 trace 和 checkpoint/recovery 数据。

AI 不再固定串行，也不是“无 token 预算自然扩片”。达到预算会产生明确 stop reason 和 coverage gap，不会自动判误报。

## 6. Coverage domain

Gap 使用结构化 domain：`scope/file/class_name/method/component/rule/operation`，并区分对正向证明、负向证明或二者的影响。

- 与候选无关的 run gap 不应复制到所有候选。
- 缺口可阻止“漏洞成立”，也可阻止“安全/误报”结论。
- AI 失败、跳过或预算延后保留规则事实，同时标记分析不完整。

## 7. Finding 状态模型

### 四层状态

| 层 | 字段 | 说明 |
|---|---|---|
| Funnel | `funnel_disposition` | 候选如何被确定性路由 |
| Analysis | `analysis_status` | AI 是否完成、失败、跳过或延后 |
| Evidence | `evidence_decision` | 证据支持、未解决、仅暴露、确定性反驳、guard 阻断或 AI 倾向判定 |
| Review | `review_status` | AI/人工工作流状态 |

`evidence_decision` 补充值：

- `blocked`：funnel 前置 guard 命中（当前 debuggable）——条件不可利用而非误报，区别于 `deterministically_refuted`（调试功能真实存在，若未来分发 debuggable 构建则高危）；候选保留可见并附 guard 证据，进入人工复核；
- `ai_likely_supported` / `ai_likely_false_positive`：AI 方向性倾向判定，不是终态——两者均映射 `review_status=pending_manual`（reason 分别为 `ai_likely_supported_needs_confirmation` / `ai_likely_false_positive_needs_confirmation`），由人工快速确认成立方向（传播/外溢）或否定方向。

正交可信度字段：

- `fact_integrity_status`：事实引用是否完整有效；
- `semantic_status`：静态语义链是否闭合；
- `exploitability_status`：是否达到静态定级或动态确认条件。

`semantic_status=closed` 只表示链路语义闭合，不等于漏洞成立；仍需授权、Guard、coverage、可利用性和 review 结论。

## 8. 版本与兼容性

- run/finding 携带 `pipeline_version`、`schema_version`；
- manifest 携带 `artifact_schema_versions`；
- v1 数据读取时补默认版本，v2 新字段均为可选消费；
- 前端保留旧 review 状态显示，不把旧状态静默改写成新语义；
- 索引自身有独立版本，不兼容时重建，而不是伪造兼容。

Repository 版本化迁移与 review 幂等/乐观并发代码已接入当前代码，但仍处于并行整合和全量验收范围；上线状态应以迁移测试、历史库抽样和完整回滚验证为准。

## 9. AI 外发与隐私

默认配置保持：`ai.enabled=true`、`ai.allow_external_code=true`。因此方法级代码切片可发送给配置的外部 OpenAI-compatible provider。

- run API 当前只返回安全配置快照：`enabled`、`allow_external_code`、协议级 `provider_kind`、`model`；不返回 `base_url` 原文、API key 或密钥环境变量名；
- 当前 `provider_kind=openai-compatible` 描述协议族而非具体供应商身份；阶段 UI 直接显示该快照值，历史 run 缺失时显示“未记录”；
- finding API 当前不保证顶层 `provider`/`model`，详情缺失时显示“Finding API 未记录”；旧 review 值仅兼容显示/交互映射，不据此猜测原始 AI 或人工来源；
- 当前 `ai_analysis` stage summary 汇总 preflight、analyzed/completed/failed/skipped/incomplete 和可选 circuit reason；正常进入候选调度时还汇总 peak concurrency，早退路径缺失该字段时 UI 显示“未汇总”；cache、stop reason、L1/L2 分轨字段若未提供，不得补造；
- 当前 `ai_analysis` stage summary 另汇总 run 级请求分账：`requests_used`、`explorer_requests_used`、`ai_stage_requests_used`、`verify_requests_used` 与 `verify_counts`；探索轨 `deep_dive_requests_used` 记在 `explorer` stage summary。早退路径只含部分分账字段，缺失时不得补造；
- 失败归因单列：`output_budget_starved`（始终思考模型 reasoning_tokens 吃满 max_tokens 的空响应，跳过 repair 直接失败）独立计数、仍计入 `failed`——预算饿死不得混入 `schema_invalid` 口径，避免"协议违规"统计失真误导定参；
- 禁止外发时，确定性规则仍可运行，但 AI coverage 可能不完整。
