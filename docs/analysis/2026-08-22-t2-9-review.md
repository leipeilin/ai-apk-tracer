## 1. 评审结论摘要

方案与大纲 §2.2/§2.5 的语义映射基本忠实，闭环四环节齐备，数据文件接通判定绕开零依赖红线的路径正确，`_sink_anchor` 的表结构与查询模式经核验可行。但存在三处高危缺口：golden 生成形状与 `GoldenCase` 严格模型不符（A-14 验收过弱）；匹配器语义（leaf 匹配、smali 规范化）未定义，与 rules 侧口径存在未声明的系统性偏离；custom 压档候选会流入 deep_dive 消耗 AI 预算且无法解除标记。回归面预判对 `write` 同名三义通用方法名过于乐观（集成测试链尾正是 `C.write`）。修订后进入实施。

## 2. 问题清单

**【R-1】【高】** golden 生成形状缺 `category/component/entry/operation/expected/must_not_report/tags` 必填字段；provenance 与 `ProvenanceRef(kind, reference)` 二字段模型不符——T4.1 消费时 `load_golden_dataset` 即报错；A-14 仅验"JSON 可序列化"过弱。
证据：backend/app/evaluation/golden.py:90-105/74-78；实施 §3.4；验收 A-14。
修订建议：provenance 改 `[{kind: "explorer-promotion", reference: "<run_id>/<candidate_id>@v<taxonomy_version>"}]`；补必填字段（category←component.kind 映射、expected 构造规则）；A-14 改 `GoldenCase.model_validate` 通过。

**【R-2】【高】** 匹配器语义三处未定义：leaf 匹配语义（rules 侧仅匹配无点裸名）/ receiver_type 规范化（smali `Lcom.foo.Bar;` 需剥 L/; 与泛型——rules `_normalize_operation_receiver_type` 已做而方案未提）/ D2 宽松命中与 rules 空值失配方向相反未声明。
证据：rules/shared/dataflow.py:2520-2536/2508-2517；indexer.py:727；实施 §3.2/D2。
修订建议：明确 leaf=末段提取语义（宽于 rules，声明漂移）或种子补 exact 集；`sink_matches_taxonomy` 内置规范化；D2 补口径差异说明。

**【R-3】【高】** custom 压档候选流入 `deep_dive_partials`（筛 partial）——custom 是 taxonomy 缺口非证据缺口，深挖补证据无法解除压档，纯耗 AI 预算并挤占真 partial。
证据：explorer.py:229-248（筛 status=="partially_validated"）；实施 §3.5 未讨论。
修订建议：`deep_dive_partials` 排除 `custom_sink_proposal=True` 候选（留人工队列走升级闭环）。

**【R-4】【中】** 种子结构缺 arity 维度——rules 侧同名同 receiver 的重载靠 arity 消歧（query@ContentResolver{4,5,6} vs query@SQLiteDatabase{7,8,9}）；方案三元组无 arities，重载误命中（漏标方向）。
证据：rules/shared/dataflow.py:3075/3094-3096；实施 §3.2。
修订建议：`SinkTaxonomyEntry` 加可选 `arities`（v1 空=不校验，结构预留）。

**【R-5】【中】** `revalidate_run_candidates` 缺 manifest_facts 来源（guard 判定需要）与 reader 重建路径；N 用例未覆盖索引缺失。
证据：explorer_validation.py:27-32；实施 §3.4。
修订建议：签名加 manifest_facts（从 run manifest 读）；reader 从 run_dir/index/code-index.json 重建；补 N-7 索引缺失降级。

**【R-6】【中】** CLI 用法 A 的 receiver 放哪个约束桶未定义；与 N-6 裸方法名叠加放大漏标。
证据：实施 §3.4 用法 A。
修订建议：默认 exact（FQCN 忠实记录），`--receiver-leaf` 显式覆盖。

**【R-7】【中】** "默认关闭"语义不完备：versions.yaml 落库即生效（自动发现=开）；关闭无配置表达（删文件）。
证据：实施 §3.5/§3.6；大纲 §2.3。
修订建议：文档明示"关闭=删除文件或路径指向不存在"（形态适配代价记录）——避免双开关歧义。

**【R-8】【中】** 回归预判乐观：集成测试链尾 `C.write`（write 在 rules 三个判定分支，种子几乎必含）→ receiver com.example.C 失配 → 误标 custom → 压档 → 集成断言 validated 失败。
证据：tests/test_explorer.py:539-546；rules/shared/dataflow.py:3009/3137/3164；验收 §3。
修订建议：既有集成测试显式禁用（settings 指向不存在路径）；A-15 专用接线测试传真实种子。

**【R-9】【低】** 并发 promote 版本递增冲突（两人同产 1.0.1）未提。
修订建议：文档注明单人操作约定 + git 层解决。

**【R-10】【低】** method_id 无 Class 段形态（`path#name:line`）未入测试矩阵；变更清单缺 schemas/config.schema.json 与 config/default.yaml 同步注记。
修订建议：A-9 补形态；变更清单补注。

**【R-11】【低】** M2 验收 4.3-1"validated≥4"指标受 custom 压档影响未点名。
修订建议：交接文档点名联动。

## 3. 认可项

1. D1 封顶 partial 忠实 §2.2 且防 custom 借 validated 进正式 finding（归一化联动自洽）。
2. §2.5 闭环四环节齐备，重校验条件链成立（A-13 覆盖 before/after）。
3. 零依赖红线保持（数据文件非 import rules；同步纪律入文件头）。
4. `_sink_anchor` 可行性核验通过（call_sites.receiver_type 列存在；查询模式与 _verify_hops 一致）。
5. 加载容错→[] 禁用兼容 T2.6 行为（A-8 对齐既有 test_custom_sink_flag_default_false）。
6. promote 幂等/base 升级/溯源元数据完整（A-10/11/12）。
7. D4 副本不落盘 + A-13 原文件不改写（save_candidates 重写风险隔离）。
8. 只判 hops[-1] 与归一化单 sink 链尾投影口径一致。
9. 种子三态结构正确映射 rules `_receiver_family_matches` 原语；D3 排除分支判断准确。
10. 纯函数下沉 backend + CLI 薄壳（sync-ai-protocol 先例）；回退=删文件粒度合适。
