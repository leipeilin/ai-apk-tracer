## 1. 评审结论摘要

两份 schema 与 T0.4 风格一致、与 §2.1 来源表及 §5.1 草案基本对齐，`entry_id` pattern 与草案示例精确匹配、`reliability` 正确映射 binder 三态。存在 2 项高严重度一致性问题（`export_status` 含无源字符串 `"null"`、`attack_surface.source` 与 `api_entry_table.source` 语义/命名割裂）及测试六类入口覆盖不全，修订后合入。

## 2. 问题清单

| 编号 | 严重度 | 问题描述 | 证据 | 修订建议 |
|---|---|---|---|---|
| R-1 | 高 | `export_status` 枚举含字符串 `"null"`，与 T0.4 receiver 产物枚举（exported/not_exported/unknown）不一致且注释自相矛盾；同一条目 `exported`(bool) 与 `export_status`(enum) 双字段并存易冲突 | `receiver_registrations.schema.json:27`；实施计划 L85/97 | 删 `"null"`；明确两字段边界：`exported` 用于 manifest 组件条目、`export_status` 用于动态 receiver 条目 |
| R-2 | 高 | attack 侧 `source` 三值（manifest/dynamic/manifest+dynamic）与 api 侧（rule_artifact:*）两套命名体系，下游 Agent1 拼接时易混淆 | 实施计划 L64/140 | 保留语义但显式交叉引用：`dynamic` ≡ `rule_artifact:receiver_registrations`（schema description 注明） |
| R-3 | 中 | 顶层 `component_type` 与 `components[].kind` 双枚举冗余且未约束相等 | 实施计划 L111/118 | 删顶层 `component_type`（文件命名已区分类型），保留 `components[].kind` |
| R-4 | 中 | 测试仅覆盖 4 类入口，缺 svc_/prv_/静态 rcv_；pattern 边界反例不足 | 验收 L20-24 | 补 3 类入口样例 + pattern 边界反例 |
| R-5 | 低 | `wv` 缩写与 `dynrcv` 全拼命名风格不一致 | 实施计划 L61 | `wv` → `webview`（对齐 kind=webview_bridge） |
| R-6 | 低 | `reliability` 含 `unknown`，binder resolve_status 无此态，属无源兜底值 | 实施计划 L83 | 删 `unknown`，保留 bound/ambiguous/unresolved/not_applicable |
| R-7 | 低 | 顶层 `package` required 策略两 schema 不一致（api 可空非 required vs attack required 可 null） | 实施计划 L51-54/107-110 | 统一为 required 且可 null（对齐 manifest 产物 package 恒有） |

## 3. 认可项

- `source` 枚举与 §2.1 来源表、T0.4 三产物文件名一一对应；`package` 顶层字段已从 §5.1 草案 `package_name` 修正为与 `manifest.py:183` 对齐的 `package`。
- `entry_id` pattern 与 §5.1 草案示例精确匹配；required 四项跨六类恒有。
- 宽松 `additionalProperties:true` 风格与 T0.4 一致；`entry_method` 可空"不伪造"符合确定性原则。
- 时序约束（api_surface→attack_surface、`api_entry_refs` 引用 `entry_id`）设计合理。
