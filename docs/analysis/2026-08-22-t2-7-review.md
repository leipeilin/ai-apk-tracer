## 1. 评审结论摘要

**总体：修订后可进入实施。** 方案框架与大纲 §2.5/§2.6 对齐（合流点 funnel 前、candidate_source 三分流、identity 分源、related_candidate_ids 关联不合并均可落地），但存在 **1 项关键缺陷**：时序前移与 `_run_ai_stage` 内 `_ai_requests_used` 置 0 重置（orchestrator.py:484）冲突，§3.5 预算影响分析与代码事实**方向相反**——实际不是"探索挤占规则预算"，而是"run 级预算总量被突破（上限≈2×max_requests_per_run）"。另有 4 项高/中严重度问题（L2 输入泄漏探索假设、guard blocked 决策语义断链、blocking_gaps notes 分支与 T2.6 实现错配、生产代码导入测试常量不可行）需编码前修订。R-1～R-5 修订后方案可实施。

## 2. 问题清单

### 【R-1】【关键】时序前移未处理 `_run_ai_stage` 的请求计数重置，run 级 AI 预算总量将被突破，§3.5 影响分析与代码事实相反

**问题描述**：方案 §3.5 断言"前移后探索先消耗预算，规则候选 L2 复核可用预算减少"并以此作为风险 R-1 与缓解措施的基础。但 `_run_ai_stage` 在 preflight 通过后执行 `self._ai_requests_used = 0`（orchestrator.py:484）。前移后实际序列：explorer（计数 0→M，orchestrator.py:904-910 检查并自增同一计数器）→ funnel → `_run_ai_stage`（**重置为 0**）→ 规则 AI 再消耗至 max。后果：① 规则候选预算不受探索消耗影响（"挤占"论述不成立）；② run 级 AI 请求总量上限 = M + max_requests_per_run，突破预算帽；③ T2.5b"防绕过计费"决定（orchestrator.py:893-895 docstring）被架空；④ `ai_analysis` stage summary `requests_used`（orchestrator.py:612，batch 预算持久化事实源）不感知探索消耗。当前代码中探索在 AI 阶段后执行，重置反而使两阶段正确共享同一池——前移后此不变量被打破。方案 §3.1 变更清单未包含对该重置的处理。

**证据**：`backend/app/analysis/orchestrator.py:484`（重置）；`orchestrator.py:77`（`__init__` 归零）；`orchestrator.py:904-910`（explorer budgeted_ai_call）；`orchestrator.py:612`（batch 事实源注释）；实施方案 §3.5、§4 R-1、§3.1。

**修订建议**：① 删除 orchestrator.py:484 的重置（`ScanOrchestrator` 每 run 新建，`__init__` 归零已保证隔离，routes.py/batch.py 均为每 run 新实例）；② `ai_analysis` stage summary 明确新口径：`requests_used` 保持 run 累计语义（=探索+规则 AI），建议分列 `explorer_requests_used`/`ai_stage_requests_used`，batch 计数逻辑同步确认；③ 验收新增 A-18：`explorer.enabled=true` + 小 `max_requests_per_run`，断言两阶段请求总数 ≤ 帽；④ §3.5 与风险表按"共享总额、探索优先消耗"语义改写。

### 【R-2】【高】"description 不进 L2 输入"为事实错误：`_candidate_summary` 白名单包含 title 与 description，探索假设文本将直通 L2 复核输入

**问题描述**：实施方案 §3.2 声称"description 不进 L2 输入——`_candidate_summary` 白名单外"。事实相反：allowed 白名单含 `"title", "description"`（context_builder.py:944），summary 以 `slice_document["candidate"] = summary` 进入 AI 输入。按 T0.6 映射表 §3（description = impact_proposal 直通），探索假设将原样进入 L2 复核输入——与大纲 §2.5"L2 AI 复核独立裁决，不受 Agent1 hypothesis 左右"冲突（锚定路径）。次级向量：severity_hint（启发式自 impact_proposal）也在白名单内。

**证据**：`backend/app/analysis/context_builder.py:942-978`（allowed 含 title/description/severity_hint）；`context_builder.py:132-153`；`docs/analysis/2026-08-22-t0-6-normalization-mapping.md` §3；实施方案 §3.2。

**修订建议**：归一化不写 description（留空，与规则候选同构——AI 完成后由 `_apply_ai_analysis` 以 analysis.summary 回填，orchestrator.py:1100-1101 既有机制）；title 保留常量"Explorer Candidate"（来源提示，无假设泄漏）。同步修订 T0.6 映射表 §3 description 行（非 required，`MAPPING` 契约结构不变，仅文档与测试断言同步——映射表 §7 纪律）。severity_hint 属候选事实层（已声明假设级并附 gap），保留。

### 【R-3】【高】guard_blocked 语义转换不完整：decision 判 blocked 依赖 `guard_blocks` 证据列表，方案只转换顶层布尔

**问题描述**：方案 §3.2 只写顶层 `guard_blocked=True`。但主链语义是**双字段**：funnel `_pipeline_requires_ai` 读顶层 `guard_blocked`（candidate_funnel.py:1124）跳 AI；decision 判 blocked 读 `guard_blocks` 列表（`b.get("type")=="debuggable"`，decision.py:880-884）——`apply_guard_verification` 的契约即"两字段必须同写同删"（guard_verifier.py:209-213 docstring）。只写布尔则 decision 不判 blocked（evidence_decision 落默认路径而非 "blocked"，severity 不会走 guard 阻断的 pending 分支），且 evidence_decision="blocked" 的 finding 语义（条件不可利用，非误报）丢失。

**证据**：`backend/app/analysis/guard_verifier.py:204-223`（同写两字段 + docstring）；`backend/app/findings/decision.py:880-884`（只认 guard_blocks）；`backend/app/analysis/candidate_funnel.py:1124`（读顶层布尔）；实施方案 §3.2。

**修订建议**：归一化候选在 `validation.blocked_by_guard=True` 时同写 `guard_blocks=[{"type":"debuggable","path":<hops[0] 解析 path>,"line":<hops[0].call_site_line>,"method":<hops[0] 解析方法名>}]` + `guard_blocked=True`（对齐 verify_candidate_guards 的 blocked 元素形状，guard_verifier.py:188-193）；验收 A-7 扩展断言 decision 层 evidence_decision=="blocked"。

### 【R-4】【高】blocking_gaps notes 分支与 T2.6 实现错配：validated 候选 notes 恒非空，映射表 §4"validated 且无上述→[]"不可达

**问题描述**：T2.6 实现中 validated 候选的 `validation.notes` 恒非空（"N/N 跳回查通过"，explorer_validation.py:80-81）。按 T0.6 映射表 §4 分支序（"notes 非空→EXPLORER_CHAIN_INCOMPLETE"），所有干净 validated 候选都会携带该 gap——与映射表 §4 末行"validated 且无上述→[]"矛盾（意图是干净 validated 无 gap）。实际影响面：gap critical=False，不拦 severity（只看 critical）、不触发 `_pipeline_has_explicit_l2_uncertainty`（只看 critical=True）、不影响 AI 路由，但名不副实（"链不完整"语义贴在完整链上），且污染候选/finding 产物。

**证据**：`backend/app/analysis/explorer_validation.py:76-100`（notes 恒赋值）；`docs/analysis/2026-08-22-t0-6-normalization-mapping.md` §4；实施方案 §3.3 blocking_gaps 组装。

**修订建议**：notes 分支收紧为"status != validated（partial/unverified 的缺口说明）或 notes 含异常语义（回查过程异常）"时才产 EXPLORER_CHAIN_INCOMPLETE；validated 全跳通过（notes 为纯成功摘要）不产。同步修订 T0.6 映射表 §4 分支条件（加"非纯成功摘要"限定）与 test_normalization_mapping.py 契约断言（映射表 §7 纪律）。

### 【R-5】【高】生产代码导入测试模块常量不可行：`SEVERITY_KEYWORDS` 从 test_normalization_mapping.py 导入依赖 pytest 运行上下文

**问题描述**：实施方案 §3.3"从 test_normalization_mapping.py 导入 SEVERITY_KEYWORDS 常量（单一事实源）"。生产模块 import `backend/tests` 下模块在部署/打包场景不可行（tests 不随生产包分发），且依赖测试收集路径。单一事实源方向正确但依赖方向反了。

**证据**：实施方案 §3.3 severity 启发式条目；`backend/tests/test_normalization_mapping.py:58-62`（常量当前定义处）。

**修订建议**：常量定义移入生产模块 `explorer_normalization.py`（SEVERITY_KEYWORDS + 分支序），`test_normalization_mapping.py` 改为从生产模块 import 并保留契约断言（防漂移纪律不降级，方向反转：测试依赖生产，而非生产依赖测试）。

### 【R-6】【中】归一化候选 summary 白名单其余字段的次级锚定与缺失字段面

**问题描述**（主 agent 核验补充）：`_candidate_summary` 白名单中 `confidence_tier`（来自三档校验档位）与 `severity_hint`（启发式假设）会进入 AI 输入；两者均已通过 EXPLORER_SEVERITY_HYPOTHESIS gap 与 confidence_tier 语义声明为假设级，属可接受的次级向量，但方案未论证。另归一化候选缺 `flow_kind` → `_deterministic_facts` 的 `value_flow_reaches_sink_argument` 恒 False（context_builder.py:981-995），AI `in_process_terminus` 反证将被交叉验证采信——方案 §4 R-3 已记录该风险但未给观察路径。

**修订建议**：方案 §3.2 补一句白名单影响论证（title/description 修正后，剩余白名单字段为事实级/已声明假设级）；R-3 风险对策补充"M2 验收覆盖指标实测时记录探索候选 ai_false_positive 占比"作为观察路径，不引入新机制。

### 【R-7】【低】验收方案 A-16 集成测试实现路径未指明

**问题描述**（主 agent 核验补充）：A-16 要求"monkeypatch AI 探索返回 validated 链"，但 API 级 run 的 analyzer 实例化路径（`create_app` → 真实 AI runtime）与 `test_explorer.py` 的 FakeAnalyzer 直注 `ExplorerOrchestrator` 是两条路径，A-16 应明确采用后者（构造 ScanOrchestrator 或直接驱动 `_run_explorer_stage` 的单元级集成），否则实施时可能误走 API 级 mock（不可行）。

**修订建议**：A-16 验收方式改为"复用 test_explorer.py FakeAnalyzer 模式，直接调用 orchestrator `_run_explorer_stage`（或构造 ScanOrchestrator 实例级）断言归一化候选并入 candidates 与产物落盘"。

## 3. 认可项

- 合流点前移至 funnel 前（大纲 §2.5 合流图的正确落地；T2.5b"AI 后"为临时安排，注释已预告）；
- candidate_source 进 facts 投影（不加排除）实现 identity 分源——利用既有 facts 投影机制零新机制，且 scope/chain 投影不受影响，探索候选与规则候选天然不合并、同 finding 不误聚合的论证成立；
- `related_candidate_ids` / `explorer_candidate_id` 加入 `_PIPELINE_IDENTITY_EXCLUDED_FIELDS` + `_TOP_LEVEL_MUTABLE_FIELDS`（保 recompute 一致性）；
- 三分流 disposition 映射（含 pending/未知值保守落 explorer_unverified）；
- partial/unverified 不进主链（D3，与 M2 验收 4.3.2"0 条进入正式 finding"一致）；
- related 匹配口径（component_name + sink 方法级 method_id，退化 (path,line)）与 M2 验收 §4.3.1"同一链"判定一致；
- funnel 三分流作为能力层交付（T2.8/T2.10 直接消费）而非只服务当前 validated 路径；
- 归一化异常单候选跳过 + 计数不中断批次（阶段主链保护模式与 T2.6 一致）；
- D1（custom_sink_proposal 延后 T2.9）：taxonomy 判定逻辑在 rules 侧（rules/shared/dataflow.py），backend → rules 零依赖红线成立，延后决策合理；
- D2（auto_promote 不消费）合理：默认 false 语义即本任务实现路径。
